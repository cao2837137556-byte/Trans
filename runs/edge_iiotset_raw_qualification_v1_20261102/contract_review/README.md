## 1. 作者证据实际给了什么

- §III-F（PDF9）说明 edge 层用数块 Raspberry Pi 上的 Mosquitto MQTT；同页也说明虚拟化层的易受攻击服务（含 DVWA）和 Node-RED Modbus。物理感知、物理 edge 与虚拟化应用角色并存，不能将“实验床含传感器”扩大为“每种攻击都以物理传感节点为受害者”。
- Table VI（PDF13）第一行温湿度：edge `192.168.0.128`、sensor `192.168.0.101`、AP `192.168.0.1`。这是固定正常候选的角色线索；没有 MAC/序列号、逐捕获地址租约或受害者跨包身份凭证。
- Table V（PDF11）及 §IV-B（PDF12–13）列 HTTP flood 来源 `192.168.0.170`、`216.58.198.74`，工具 slowhttptest，文称使用 200000 connections 的 GET requests。没有给这两个 PCAP 的精确受害目标 IP/MAC、命令行、事件起止或 Wireshark/BPF 包筛选器。
- UDP flood 来源列 `190.123.219.128`、`16.226.184.201`、`153.125.214.15`、`91.184.12.91`，hping3-based script；正文明确 UDP 攻击可以伪造源地址。源 IP 因而不是物理攻击机身份凭据。
- §IV-A（PDF11–12）说明正常与攻击都在 2021-11-21 至 2022-01-10 不同小时/日期产生；正常不连续，一次捕获最多3小时。没有逐事件时间表，既不证明正常先于攻击，也不证明任一文件完整达到7200秒。
- §IV-A 的标签说明是在派生 CSV 中增加 Attack_label/Attack_type。它没有建立“攻击 PCAP 的所有包都为直接恶意查询”的原始包真值规则。

## 2. 下载正常包前的可执行门

先完成固定两攻击包的完整容器/方向/角色检查，再判以下三种状态；这一步不需要模型分数。

|状态|充分触发条件|后续|
|---|---|---|
|`STOP_TARGET_MISMATCH`|可识别的主要攻击向 HTTP request / UDP 流量实际指向其他地址/目标，未对应 `0.128` edge 或 `0.101` sensor；尤其已能确定目标属于另一 VM/服务器或另一场景|不取温湿度正常，不换其他正常文件，不扩大三包卡|
|`STOP_TARGET_OR_DIRECTION_UNRESOLVED`|无法把流量与论文攻击行为、直接方向或合法物理目标相连；例如只有文档来源名单但实际角色反转，攻击事件全靠整文件标签，或所需直接非守卫TCP/UDP人口为0|保留未知/失败，不先取正常来碰运气，不把反向响应充数|
|`CONTINUE_FIXED_NORMAL_FOR_IDENTITY_AND_CLOCK_CHECK`|两攻击中的候选方向/目标实际对应固定场景，至少存在可审计的物理 edge/sensor 角色证据且无明显 VM/其他端点矛盾；正常尚须用MAC/真实时钟核对|只取已经固定的温湿度正常；此状态仅允许完成资格查验，绝不是主确认 PASS|

同 `192.168.0.*` 网段、目标名像 IoT、端口80/1883、少数无关包碰巧出现 `0.128`，均不足以走第三行。候选目标应由实际攻击行为/方向主群体与文档角色对应，报告全部目标及计数；不能只保留命中的少数包以凑配对。

若容器为 Linux cooked/all-interface、缺少端点MAC或同IP出现多个MAC，应显式记录身份未闭合，不能用MAC缺失当作默认同一台物理Pi。MAC OUI可以辅助，但OUI或相同MAC也不能单独证明物理设备型号/跨时间唯一性；VM地址或其它冲突需要保留。

## 3. ACK/UDP 标签应分四层

1. `ALL_CAPTURE_CONTEXT`：全部原始包，只作容器、时钟、方向与上下文人口，不整文件改成攻击。
2. `DOCUMENTED_SOURCE_DIRECTION_CANDIDATE`：论文列来源与实际目标/协议相符的正向候选；源匹配不是最终逐包恶意真值。
3. `DIRECT_ATTACK_BEHAVIOR_CANDIDATE`：HTTP实际请求行为（含可审计GET/POST及目标）或与UDP flood描述相符的正向发送群体；计数 TCP flags，并把 `ACK=1 & SYN=0` 与 SYN/SYN+ACK 等分开。HTTP纯握手ACK不能仅凭flags升级成恶意载荷；若请求跨TCP段，未重组请求数只作为可解析下界，不擅自充总量。
4. `CONFIRMED_DIRECT_ATTACK_TRUTH`：只有具备足够官方事件/目标/方向规则并与原包对齐，才登记可用于保护评价的真值。当前论文文本本身没有闭合这一层。

反向 ACK、HTTP response、UDP/ICMP受害者回复要另列，不能加入第三/四层以证明非守卫攻击保护。攻击文件中不匹配候选的背景包也不能反过来当可信正常或补参考。

HTTP节未像UDP节一样明确声称伪造源，因此不能为了让TCP实际来源与表不一致而自动套用“源伪造”解释。表中的公有地址本身不构成冲突，也不能凭地址外观推断为云服务器/攻击机；如果实际会话显示文档所列“来源”是对端服务，应该登记 `SOURCE_ROLE_CONFLICT`，不自行把表翻转成新的真值规则。

Table VI 的 `192.168.0.101` 是正常 sensor；但论文其他 DNS/ARP 场景（PDF14）又把同IP列为攻击来源。它证明地址角色必须按捕获/事件核对，不能全数据集共享静态 IP→设备/攻击者映射；这不直接证明数据造假，也不授权删掉冲突包。

## 4. 正常包取得后仍需的硬门

- 同目标物理身份/MAC及原始上下文确实对应；edge 与 sensor 分账，不把 server 召回写成 sensor 召回。
- 全量实际时钟证明可信正常早于两个拟确认攻击；完整未预过滤7200秒入网，且仍有合法后段正常，不能拼接离散日期或平移时间。
- 同协议真实合法组件覆盖；UDP全无合法参考导致RAW回退时，零撤警不提供C5启用状态的UDP保护证据。
- 原接口/链路类型、时间倒退、缺口、截断、同接口/多接口重复、独立设备/事件数量与血缘排重。
- ACK/UDP最终真值层若仍未知，状态为未资格，不运行冻结C5以试分。
