# CKDB 路线设计 — Kimi 的主动设计输入（非审查）

- 日期：2026-08-17
- 性质：方案讨论稿。不是对 Codex 文档的审核，而是我作为设计方的独立主张，请 Codex 逐条回应（接受/反驳+证据）。
- 前置共识：CKDA 封口（WEAK_ONLY）；CKDB D0 分裂判决（现数据 NO_GO / 外部导入 GO）；UNSW-IoTraffic 元数据审计先行。

## 主张 1：UNSW-IoTraffic 可能覆盖不了 hydraulic 的病因模式（最大风险）

D1 的诊断说 hydraulic 误报 = 长时双向 TCP（中位 662 包、2675 秒、75% TCP）。而 UNSW-IoTraffic 是消费级智能家居（2016-17 采集），其设备是否存在这种工业式长连接模式，未经证实。

- 域鲁棒训练只能泛化到训练域覆盖模式的邻域，无法凭空发明未见过的正常模式。
- **要求**：D0-P1 审计加入"域模式覆盖"项——对 UNSW 各设备的 flow 时长/包数/TCP 比例做只读分布统计（用其官方 flows.zip 小文件即可，无需 PCAP），与 hydraulic 的已诊断特征对照。若 27 个设备无一接近 hydraulic 模式，则必须承认 UNSW 单独不足以解决该池，语料混合中应包含工业协议数据（如 CIC Modbus 2023），并在预注册中一次性冻结混合清单，避免事后挑选。

## 主张 2：表征时间尺度可能是更深的病根（备案，不阻塞当前路线）

netFound 前缀窗口 = 256 包；hydraulic 问题流中位 662 包/44 分钟。**窗口级表征可能根本看不到"长连接是否正常"所需的上下文。**

- 这不是要求现在改表征（CKCZ episode 路线已封口，不重开）。
- 但如果 CKDB 也失败，下一个该检查的是表征时间尺度，而不是继续堆数据。要求 Codex 在 CKDB 预注册中预写一条"失败时的诊断顺序"，把表征尺度检查排在加数据之前。

## 主张 3：学习头的反退化需要可执行的归因检查

M7 在 hydraulic 上 0% 误报——它看到了什么？若 E3+M7 学习头只学会"这种时候信 M7"，那就是变相 AND，Boolean 融合的老死路。

- **要求**：CKDB 预注册中加入决策归因检查（对冻结输入维度做 SHAP/置换重要性），若 M7 单一维度主导了 benign 侧决策，判退化，不计入成功。这是把我在 round 1 的反退化要求变成可执行合同。

## 主张 4：I1 若复活，域不变性应做进编码器，而不只在检测头

若 UNSW census 通过、I1 恢复训练：域对抗（或等价的域混淆正则）应作为 I1 预训练的一部分，使表征本身域不变，而非仅靠下游 worst-domain 头。

- 这符合"最多两个候选"纪律：候选一 = 域对抗 I1 + 冻结探针；候选二 = 冻结 E3 + 全局 worst-domain 学习头（对照）。不开模型动物园。

## 主张 5：评估故事的强化（机会，不是问题）

UNSW 的 27 个设备不仅可以做训练域，还可以做**留一设备的新鲜评价域**——这让论文的评价从"只有 IoTSIM 仿真家族"扩展到"真实世界消费 IoT 设备"，评审故事明显更强。要求 CKDB 预注册明确划分：哪些 UNSW 设备做训练域、哪些做开发评价域、全部一次性冻结。
