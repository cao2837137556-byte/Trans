# v2 的 P/T/K 内存核对与资源决定

2026-09-29。用户报告 Job177491 因内存等待至 10-01，node188 可申请约155G、CPU充足；本次未远程核实调度状态。用户条件：有把握峰值低于130G才出150G资源包，否则维持192G。

**决定：维持现有192G，不制作150G包，不取消或重提177491。** 当前账目表明实际内存很可能远低于192G，但不足以有把握保证全部P/T/K低于130G。主要缺口是16个E3进程的目标机加载/推理/分配器峰值及主进程残留，不是小检测头参数太大。不以“推测够用”替代用户要求的可信余量。

## 依据和估计性质

已核对已审v2源码、配置、原有元数据样本、静态回执及本地checkpoint的safetensors头部；未读取权重张量、未构造模型、未运行PCAP解码/前向/训练/资源试验。包及43个模块pins一致，SHA仍为7087d73186693ad4c8482027b82ce2f4b6027ed5c1c290045b44a8f0ddef2768。算术脚本及输出见 `runs/legacy_continuous_input_memory_review_v2_20260929/estimate.py` 和 `estimate.json`。

下文GiB均为2^30字节。Slurm的G请求按其内存单位解释，不能与十进制GB混用；若用户130G是十进制130GB，要求会更严格，决定不变。以下区间是带明确假设的规划预算，不是实测峰值、统计置信区间或硬上界。

静态可确认量：

- checkpoint为698,780,900字节；头部记录174,683,335个参数元素，按float32约0.65075GiB。16份算术和10.412GiB，不包含Python/Torch、加载副本、计算临时量和内存碎片，也不等同于物理内存去重后的占用。
- 最大特征batch为16×12×73。一个隐藏张量16×876×768×4约41.06MiB，一个burst注意力矩阵约46.84MiB。E3调用base_transformer，inference_mode，不计算MLM词表logits、不留训练梯度、不输出全层hidden_states。因此不能误按16份大模型训练内存估算，但也不能只算一个隐藏张量。
- 对LEARN/CIC_DEV/UNSW_DEV各取前1024条原metadata，用CPython3.9逐行对象图字节估算，外推总计约4.545GiB；加参考、容器、FIT标记与分配开销，预算一份约5–6GiB。是样本外推且未覆盖所有长字段，不是全量上界；实际Linux版本/对象共享也会不同。
- 全部1,095,200×794 float32新特征约3.239GiB；LEARN新/旧矩阵分别2.268/2.194GiB。np.memmap不等于永远不占物理内存，访问后的页及文件缓存仍须考虑。
- K的三个CAL高级索引副本合计约1.292GiB，不能按三个view当零拷贝。

## 分阶段峰值预算

| 阶段 | 规划预算（GiB） | 组成和限制 |
|---|---:|---|
| P：四捕获审计及正式decode/spool | 15–60 | 约5–6元数据；给新旧状态表/索引约5–25；解码器、Python碎片、SQLite缓存/排序、文件缓存等约5–29。后一部分未实测，不是可证明上界。 |
| P：16个E3特征worker | 常规假设63–105；保守情景121–163 | 常规假设每worker3–5，加主进程/系统余量15–25；保守情景每worker6–8，加余量25–35。这些worker值是敏感性假设，不是观察到的占用。 |
| P：合并与FIT归一化 | 15–40 | 无16个E3并发；元数据、新矩阵mmap、旧矩阵页、4096行float64归一化临时块、前阶段分配器残留及文件缓存。 |
| T：最多4个训练worker | 40–80 | 主进程+4worker各持有全metadata，预算约25–30；保守重复计旧/新LEARN驻留页约18；权重层级树、索引、库运行时及父进程残留/缓存余量。检测头和AdamW状态很小，不是主要占用。 |
| K：源CAL后两池顺序评分 | 15–40 | 单主进程、全metadata、约1.292GiB CAL副本、特征页、359875对校准索引、分数组合、逐组件报告临时对象及残留/缓存。所有小head加载一起仍很小。 |

状态表、spool重建、16个E3worker、4个训练worker不是全部同时运行；按阶段最大值估计，不相加。四个优先捕获也是依次解码，没有额外4个解码器并发。

**状态与spool特别核对：** RecentState内部每方向12 bursts×6 packets，最多保留144行，输出才截为72；同帧重放的旧ScopedPrefixes另可留144个精简行。namespace的last_seen/poison/tombstone还单独占用。状态按捕获处理，不累计全部219个捕获；但物理GC只在表容量压力下发生，且Python释放后不保证RSS完全归还。最大捕获有5,762,819帧，一百万namespace上限不是字节内存上限。旧回执里的sessions是旧选择/标注流程计数，不能直接当全部上下文活跃键的严格上界。

SQLite spool主体写磁盘，并非全部加载到RAM。形状排序的fetchall只取UID/protocol/width/bursts约109.5万条，worker每batch只读不超过16个body，特征输出积累1024行就提交。仍有SQLite排序/缓存、mmap与内核页缓存、Python容器开销；不能把160GiB输出限额加成160GiB内存，也不能把spool算成完全零内存。

## 为什么不足以改150G

P特征阶段可写成 `峰值 ≈ 主进程及余量 + 16×单worker峰值`。若前项25GiB，要保证总计低于130GiB，单worker必须低于6.5625GiB；若前项35GiB，则必须低于5.9375GiB。当前源码张量量级支持“可能足够”，但没有目标Linux/Torch2.5.1上足以约束这个峰值的证据。每worker多1GiB会放大为16GiB；不能为赶排队选择乐观端点。

现有numeric_probe只有33个生成输入、三次真实前向，主要验证数值及耗时。代码没有记录单worker最坏形状的独立峰值，也没有验证16进程同时加载及多形状长期分配器残留；目前本次作业尚未跑到它。以前其他作业的batch/输入/并发/模块生命周期不同，单个MaxRSS也不代表本链全部进程树，不能直接拿来担保。

内存检查是Linux进程树RSS求和，可能重复计入共享映射，同时不覆盖所有cgroup文件缓存/内核记账。Slurm约束与此不是同一计数器；把176改成130或138只会改变停止条件，不能证明不会被Slurm OOM杀掉。训练worker独立限额32GiB，而feature_worker实际使用整链limits，并没有一个6GiB单进程承诺。阶段监控每隔一段时间采样，也不是瞬时峰值证明。

因此按用户分支选择保留192G/整链176GiB保护/训练worker32GiB，16特征worker、4训练worker及所有科学设定不变。未创建新包、未上传、未取消或修改调度作业。10-01仅是用户报告的当前预计开始日，不保证调度时间不变。新的资源试验或减少并发不属于本次“只改--mem”的范围，本次不启动。
