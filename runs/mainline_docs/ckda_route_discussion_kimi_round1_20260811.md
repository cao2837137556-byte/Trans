## 1. 总体判断：方向正确，同意升为主线

核心理由成立：CKCZ 的死因是"只聚合已有判断、没有新增信息"，已在 87,730 个 oracle 点上被完整证明；CKDA 从原始包序列提取新表征，是目前唯一**信息论上有新来源**的路线。三段式 staging（D0 按兼容性选模型、D1 便宜 canary、D2 才动损失）符合"早死早超生"原则。对导师损失函数的定位（信息不存在时损失救不了，CKAA/CKBW 已有证据）判断准确。

## 2. 必须提前钉死的四个点（建议纳入 CKDA-D0/D1 设计文档）

1. **D1 的"信号"判定必须预声明、且承认非对称性**。线性探针只测线性可分性：探针有信号 → 路线有信息（绿灯）；探针无信号 → **不能判死刑**（信息可能非线性存在）。建议 D1 预声明两个探针（线性 + 一个小型固定结构 MLP），两者皆无信号才判 NO_INFORMATION，避免误杀。canary 指标、kill 标准、"无信号"定义必须在看到任何 embedding 之前冻结。
2. **预训练数据污染审计进 D0**。ET-BERT / YaTC / netFound 的预训练语料必须审查与我们评测数据（IoTSIM 合成、ToN-IoT）的重叠风险；若编码器在预训练中见过我们的测试分布，canary 信号将不可信。D0 的兼容性表必须加"预训练语料来源与重叠风险"列。
3. **因果性要从"能力"升级为"合同"**。session-prefix 表征必须严格因果（只用当前事件之前的包），D0 只确认模型支持截断还不够——D1 实现必须有单测证明无 lookahead（例如：改变未来包，当前 embedding 逐位不变）。
4. **工程成本写实进 D0**。CKDA 本质需要 PCAP 解码拿到包序列（CKCZ 的 cache 只有 target 行元数据，不够用）。D0 应估算：24+31+ToN 合法/VIEWED 源的解码量、编码 30 万+ 记录的 GPU 需求、HPC 队列匹配度。**FINAL（cooler-motor）PCAP 一律不解码**——这条要写进合同。

## 3. 同意项

- 按兼容性而非结果选模型，且选择必须在见到任何 embedding 之前完成。
- 51D MiniRocket 只做便宜对照，不做主攻；机制专家、按机制分阈值不做主线（防 family 补丁）。
- D2 的损失消融必须单变量（CE vs 新损失），损失必须是统一机制，禁止按已见失败 family 加权。
