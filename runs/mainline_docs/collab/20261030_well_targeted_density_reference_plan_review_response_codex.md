## 1. 回复问题一：V3 参考的构建参数已能查清

依据：[密参考冻结协议](../../dense_reference_matrix_v1_20261027/PROTOCOL.md)、[V3 实现](../../../repo/ood/constrained_onboarding_core_v3.py)。

- 源参考来自六台源设备的 **13 段早期 REFERENCE 正常 capture 区间**，不是后续 FIT/CAL 查询。协议明确禁止把后续 FIT/CAL 查询挪作这套参考。
- 目标参考来自原 B2 冻结的入网观察窗口，不延长、不按结果改窗口。
- 每设备、每协议至多 4,096 个位置；保留旧锚点，以组件轮转、组件内时间均匀和固定盐 `claude-dense-reference-r1-20261025` 的 SHA256(UID) 排序选择，不按分数或标签选位。
- SOURCE_REFS 的 4,728 个合法位置全部入库；A 的 8,574 个全部入库；B 的 45,136 个位置中选了 13,247 个。三库共 26,549 行，其中新增 E3 21,660 行。
- 没有常规 kNN 的可调 k。对每个查询，先要求至少两个**真实不同且因果合法的组件**，然后取不同组件的第二近代表。

实际支持计算为：归一化 E3 的余弦距离 `dz`、q14 的 RMS 距离 `dq`，使用各协议的两个半径，`joint=max(dz/rho_z,dq/rho_q)`；跨不同组件取得 `second_joint`，再令 `support=clip(1-second_joint,0,1)`。不足两个组件会在距离/支持计算前退出。

主阶段保存的 [geometry.json](../../diagnostics_d1_d2_v1_20261022/assets/onboarding/run/evaluation/calibration/geometry.json) 为：

| 协议 | rho_z | rho_q |
| --- | ---: | ---: |
| TCP / 6 | 0.6350346595136246 | 0.3784318683067434 |
| UDP / 17 | 0.538951893262028 | 0.27275012216397504 |

其本地 SHA256 为 `080c069fa41f6eb7fbcea2e890873be462f8471b8ff2a039a8a30935674ca124`，与 [179602 源 seal 别名](../../dense_reference_ab_stage_candidate_v1_20261028/preparation_r2/SOURCE_SEAL_ALIASES.json)及 [A/B 候选绑定](../../dense_reference_ab_stage_candidate_v1_20261028/config/MATRIX_CANDIDATE_HPC.json)一致。这是历史主阶段六源设备共同拟合的几何，不是 G0/G1 折内几何，不可直接充当新源折的参数。

因此现稿“0.5 倍 support 半径的 E3 去重”和“2 倍 support 半径的攻击禁区”尚无唯一含义：须明确采用哪个距离轴、协议、normalizer，以及是否使用上述联合距离。半径数值已找到，并不能补齐这个定义。

## 3. 回复问题三：不能把“最低 10% 攻击、每设备 50 行”当成保护已补齐

当前能确认上述 FIT 全体攻击行数，以及 G0 CAL 攻击 8,525 行、G1 CAL 攻击 107,147 行；**本轮没有取得按新方案定义的逐设备近边界攻击数量和 margin 分布，不填推测数字。** 原稿的边界定义也尚未确定：按哪个头/集成 cut、攻击还是正常分位总体、“cut 附近的 10% 分位宽度”如何唯一计算，均会改变集合。

这些总数不代表存在足够有效保护样本。最低 margin 的 10% 攻击可能包含大量 RAW 原本已漏检的样本；真正需要保护的是**当前头原来检出的攻击**，其中还要看合法参考资格、scale 和最大允许修正是否足以把分数压过实际 cut。50 条同会话样本也不等于 50 个独立保护例。`min(50,可用数)` 甚至允许零条，标注“覆盖不足”本身不是通过条件。

更直接的问题是角色重用。现有 S 定义就是：G0 头在 G1 的原 FIT 上评价，G1 头在 G0 的原 FIT 上评价，即各自的 **HELD∩原FIT**。现稿把同一集合用于补 CAL 攻击、挑密度档位，随后又说“冻结后 S 看一次”。它不能同时充当开发材料和未参与选择的最后源检验。现有 S 已被开发观察的披露应保留，但披露不会消除这次新拟合/新选型的重用。

如果未来有真实新增材料，应一次写清 head/device/UID/session/component 的开发、保护校准、选型及最后检查角色；若整个旧 S 用于开发，就如实报告开发成绩并另找合法检查材料，不能只换集合名称。此处不是要求把既有开发池重新说成独立测试集。

另外，§2 要远离 FIT **任一攻击**，§3 只定义**最低 margin 10% 攻击**禁区，两者须选定一个。远离已知 FIT 攻击只能形成经验假说，无法保证未见设备的攻击不被正常参考覆盖。

## 4. 上界数字的解释及剩余规格

用户转述里的“TP Link 免费全消掉，B 仍约 6.87%”有口径混淆；**well 正文 §0.2 对 6.869728% 的设备级描述是正确的。** 它是特定“单组件＋已有正支持”消除范围下 TP Link 自身的剩余 FPR 下界。若把 TP Link 全部误报免费消掉，B 整体仍为 `9.5196539487%−1.8577512348pp=7.6619027139%`。

[既有上界表](../../ab_reachable_bounds_readonly_v1_20261028/RESULT_REVIEW.md)还说明：“单组件＋已有正支持”只对 A 的池＋设备目标尚未排除；B 的池幅度下界虽是 1.715144%，TP Link 设备仍 7.230553%，完整目标已排除。在既有五种范围中，纳入全部合格双组件、含原零支持的最大组合，才对两池完整误报目标均尚未排除。此结论既不证明实际补点能达到，也不证明攻击安全；若引入新参考资产，旧固定资产上界也不能直接当作新算法可行性证明。

材料与角色问题解决前，不建议继续细修档位。若将来形成修订候选，还应一次补齐：

- 恢复每设备 FPR≤2%、池召回≥99%，以及相对 RAW 的累计保护和原分母；保留设备1pp、activity/annotation5pp、三 seed 与 ensemble、适用的 own/donor 和源 phase 交叉组检查。RAW 已低于99%的源组不再撤回原 TP；其他组的99%条件也要完整保留。不能只计算179700→新候选的增量来替代累计伤害。
- “三档全部评估后选安全最优”与“任何源门失败立即结项、不调档”目前冲突。明确采用三候选固定有限比较还是预先唯一选档，并固定 δ、排序、并列规则及不足样本的停止条件。
- 不训练神经网络仍可能包含监督参考选择、攻击距离计算和重复支持评价。4CPU/8GiB、源4h＋条件目标4h要有实际候选规模下的预算依据，不能靠“不训练”保证。
