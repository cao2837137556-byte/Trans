## 3. B：只清点三台，摘要确有多连接线索

来源为[UNSW-IoTraffic官方介绍](https://iotanalytics.unsw.edu.au/unsw-iotraffic.html)、[Dryad数据集](https://datadryad.org/dataset/doi:10.5061/dryad.w0vt4b94b)，DOI `10.5061/dryad.w0vt4b94b`。发布许可CC0。它是2016—2017年实验室设备流量，与当前B使用的2018年Attack Traces不是同一批原始文件。

本轮复用本地官方 `flows.zip`，**95,513,089字节及完整SHA与实时官方API一致**；只流式分析三台成员，没有解压或遍历其余设备的流量内容。三成员合计203,178,180字节未压缩CSV，883,299行；各成员SHA与历史封存清单相符。机器输出：[B_FLOW_METADATA_RESEARCH.json](../../targeted_normal_data_research_v1_20261030/B_FLOW_METADATA_RESEARCH.json)。

| 设备 / MAC | 摘要流行数 | TCP行 / UDP行 | 不同TCP五元组 / UDP五元组 | 有流起点的日期数 |
| --- | ---: | ---: | ---: | ---: |
| WEMO Power / ec:1a:59:79:f4:89 | 490,562 | 229,729 / 42,030 | 14,324 / 2,041 | 105 |
| Samsung / 00:16:6c:ab:6b:88 | 379,921 | 78,275 / 61,573 | 24,119 / 20,848 | 119 |
| TP Link / 50:c7:bf:00:56:39 | 12,816 | 10,600 / 2,209 | 511 / 2,055 | 32 |

不同五元组只计TCP/UDP、IPv4及合法端口的摘要行；三台合计150行TCP/UDP记录没有通过这个字段级代理检查。TCP/UDP不是全部协议，因此这两列不要求加总为全部流行数。120秒超时切出的多条flow已按无向五元组归并，未把flow行数当作独立组件数。

这些数字是**依赖发布方设备文件归属的元数据代理**，不是已通过当前原始前端的参考数。通过源IP或临时端口变化形成很多键，也不证明业务种类丰富或统计独立；它只支持“值得检查原始包是否有实际新增覆盖”。

观察到的内容线索：WEMO有大量TCP/49153及发布方标为HTTP的记录；Samsung有TCP/80、5222等；TP Link的10,600条TCP中10,511条涉及50443端口，主要是云端通信线索。应用协议名由发布方解析器产生，不据名称认证请求语义或正常性；CSV未提供当前查询所需的SYN/ACK/FIN/RST逐包阶段，因此尚不能证明包含要补的阶段。

### 必须核实的三项质量问题

1. **三台全部883,299行的srcMac/dstMac均为null。** MAC目前来自官方设备清单和文件名，并非CSV逐行验证。可能是派生提取层信息缺失，不能直接断言原始PCAP也缺MAC。原始资格核验必须看linktype、帧内身份与归属；不得靠猜MAC补字段以绕过当前前端。
2. **流持续时间与README声明的秒单位存在不一致。** 按文档秒单位解释，WEMO/Samsung/TP Link分别有608/320/80条记录持续时间超过整个203天采集跨度，最大值甚至达7,596,278,173。不能自动除1000修正，也不能用`time+flowDuration`认证参考截止。CSV流起点均早于当前B截止，但参考真实末帧时间必须回到PCAP核验。
3. **正常性证据有限。** 官方说明是setup、idle、interactions和自主后台通信，没有逐事件/逐交互真值；未描述攻击树不等于对每行作了无攻击认证。可作为日常正常来源候选继续核验，但要声明其来源级正常假设，检查研究采集说明、实际日期/身份和明显污染风险，不能用模型低分认证正常。设备MAC一致也不自动证明跨年物理身份、固件和环境完全一致。

这里没有发现足以宣告原始PCAP不可用的证据，也没有发现足以将其直接晋升为可信参考的证据。**推荐状态是 `RAW_QUALIFICATION_CANDIDATE`。**
