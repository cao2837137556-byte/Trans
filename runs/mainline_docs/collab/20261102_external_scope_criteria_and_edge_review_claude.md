# 外部测试的适用范围条件，以及对 Edge-IIoTset 三包回执的意见（Claude）

2026-11-02。依据：[Edge-IIoTset 三包资格回执](20261102_edge_iiotset_three_file_raw_qualification_codex.md)、`runs/edge_iiotset_raw_qualification_v1_20261102/RESULT.json`、[改进反馈](20261102_working_feedback_for_codex_claude.md)第 5 节。用户已同意本稿的方向。

## 1. 用户的决定

1. 外部数据集**按方法的适用范围选择，不按难易选择**。凡是通过下面范围条件的数据集都纳入评价，结果全部报告。
2. Edge-IIoTset 在标签和上下文复核通过后，作为**外部测试 1**。
3. 只有一台目标设备不足以支撑一区或顶会的泛化结论，所以**还需要外部测试 2**。由 Claude 先调研候选，Codex 复核，候选清单见同日的 `20261102_external_candidate_survey_claude.md`。

## 2. 适用范围条件（预先登记，所有候选一视同仁）

下面每一条都只看数据本身和采集文档，**不看任何模型输出**（分数、FPR、召回、support、距离都不看）。

| 编号 | 条件 | 判定依据 |
|---|---|---|
| S1 | 目标是 IoT 或边缘网络设备，有可识别的 L2/L3 身份 | MAC，或者有文档支撑的固定 IP；如果是 Raspberry Pi 或边缘服务器，写明它的角色 |
| S2 | 原始 PCAP/PCAPNG 可用，真实时钟可用 | CSV 或流特征不合格 |
| S3 | 同一目标在第一次被评价之前，有可信的正常流量：观察窗 ≥7200 秒，之后还有正常查询 | 沿用现行合同；不拼接、不平移时钟 |
| S4 | 有针对该目标的攻击，并且能定出合法标签 | 攻击方向、时间区间或官方过滤规则可以落到具体包上；整个文件统一打标签不合格 |
| S5 | 威胁模型内的攻击类型 | 洪水、扫描、暴力破解、僵尸网络 C&C 等网络层可见的攻击；纯载荷类、物理类攻击不在范围内 |
| S6 | 与 A（CICIoT2022）、B（UNSW 2018）以及历史补库不重叠 | 逐个核对 MAC 和来源 |

**难度只描述，不用于筛选。** 下面这些数据层面的事实应该算出来写进报告，帮助读者理解结果，但不能用来决定纳入还是排除：
- 攻击所用的协议或端口在正常流量中是否出现过；
- 正常流量的协议构成；
- 直接攻击 ACK 的占比。

## 3. 对 Edge-IIoTset 三包的四点意见

1. **结论范围。** 只有一个目标 `192.168.0.128`，是 Raspberry Pi 上的 MQTT 边缘服务器。论文里只能写"一台边缘设备、两类洪水攻击"，不能写成 IoT 终端，也不能写成多设备。
2. **请算出难度描述（第 2 节），写进复核回执。** 这台设备的正常流量里，TCP 占 1,332,428 条，几乎都是 1883 端口；UDP 只有 2,430 条。请核实 HTTP 攻击的目标端口（是否 80）在正常流量里出现过多少次，UDP flood 的目标端口在正常流量里又出现过多少次。如果攻击都落在"正常时从未出现"的协议或端口上，结果大概率很好看，这一点必须在论文中写明，不能当作强证据来用。
3. **标签规则要在评价前写死。** 回执里的 88,280 条 HTTP ACK 候选、2,898,830 条 UDP 候选都只是推断。请在执行卡里固定以下三点：
   - 直接攻击包的判定式，规定方向、端口和标志位；
   - 攻击文件中不属于攻击方向的包如何处理：建议排除，既不算攻击也不算正常；
   - 是否按事件报告，还是按包报告。
4. **"历史参考"的适配方式也要写死。** A/B 的参考来自其他年份的公开数据；这里只能用同一份正常抓包的前段。请在执行卡中写明：
   - 参考取自哪一段，以及观察窗之后的正常查询从哪里开始；
   - 正常流量中超过一小时的间隙怎么处理：建议在间隙处切开、各段独立，不能跨间隙拼接；
   - 论文中把这种情况明确称为"同一捕获的早期正常"，与 A/B 的"跨年份历史"区分开。

以上四点落实之后，Edge-IIoTset 的执行卡才能冻结。冻结之前不跑任何模型。
