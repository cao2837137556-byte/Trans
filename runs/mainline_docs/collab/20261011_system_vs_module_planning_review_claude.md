## 1. 附加统计的 UID 与权重口径：通过

- **数值一致。** 两个池和 7 台设备的 RECENT ensemble 加权 FPR，附加报告与官方评价器的最大绝对差为 **0**（共 9 个值）。设备级都在设备内重新归一化，与官方口径相同。
- **权重。** 权重为 `1/label_metric_weight_denominator`，并检查每类质量和为 1。资格内外的拆分质量和设备分组质量都做了守恒检查。
- **UID。** 先验证 UID 集合完全一致且无重复，然后按 UID 显式重排，不按数组位置对齐。缺失、重复、多余的 UID 都会被拒绝。决定和资格 mask 要求类型为 bool，且形状正确。
- **未来模式的路径对得上。**
  - `prepared/{pool}.jsonl.gz` 来自 prepare 的复制（prepare_v2:161）；
  - `{pool}/decisions.npz` 来自 evaluate 的写出（evaluate_v2:101）；
  - export 只省略 `prepared/*.npy`，jsonl 会随结果拉回。
  - 标签、设备和权重漂移都会停止；R0 必须与父 RECENT 逐位相同，这与 evaluate 中 `R0_ORIGINAL_DECISION` 的检查一致。
- **资格 mask 取自父 run。** 资格只取决于查询与参考的元数据，与头无关，所以在新头上沿用是正确的。
- 边界情况的处理与回应文档一致：H=0、s=0、所需收益大于 1 时保留真实值、设备级目标 2%。

## 3. 非阻塞建议

### 3.1 明确“零新增漏检”的角色

`proposed_module_pairing.added_attack_misses_required = 0` 目前写在“模块配对”一节下，没有说明它是整套系统的验收门槛，还是只作为“模块安全”这一表述的条件。用户最关心的正是“入网模块会放掉攻击”，建议在草案中写明它是**整套系统的验收门槛**：三个 seed 加 ensemble，两个 A 池和 UNSW 各自判定，任一处不满足即 FAIL。

### 3.2 附加报告中加上攻击侧的资格份额

目前只报告了正常侧的 s。模块只能在有资格的查询上撤警，所以有资格查询上的攻击 TP，就是可能被它误撤的全部范围；回退区的攻击天然受保护。建议同时报告：
- `attack_TP_eligible_share`：基础头的攻击 TP 加权质量中，有资格的比例；
- 逐设备的同一指标。

我对 RECENT ensemble 做了只读计算：CIC 为 66.7%，UNSW 为 60.0%。也就是说，零新增漏检约束要保护的是约六成的攻击质量。它与正常侧的 s 一起，决定模块在每台设备上能得到多少收益、要承担多少风险，下一版模块设计会直接用到。

### 3.3 三设备缓存：缓存键补上解码器身份，并加一项与父特征的一致性回放

- **缓存键。** 现有键包含算法版本、捕获身份、E3 检查点、UID 清单、参考预算、代码身份。建议再加上**解码器身份**：TShark 版本、重组相关偏好、解析器版本。Job177491 的停止正是由 TShark 首分片重组的行为触发的，同样的代码换一个解码器版本，就可能得到不同的 token。
- **与父特征的一致性回放（建议作为准备阶段的硬条件）。** 冻结头是在 Job177891 的 FIT 特征上训练的，三设备的新入口必须产出语义完全相同的特征。三设备池与已有角色共享 7 个 Active 捕获，所以可以：
  - 事先登记一个固定样本：从这 7 个共享捕获中，按 UID 哈希抽取例如 1,024 条已封存的父行；
  - 用新入口重算这些行，要求与父 run 的特征 **float32 逐位相同**。

  这与 09-22 预检中的 `EXACT_FLOAT32_EQUAL` 回放是同一种做法。如果父特征因磁盘故障无法恢复，就写明这项检查无法执行，并改用合成数据的一致性检查，不能默认两者等价。

### 3.4 资源假设：P 阶段按字节估算；内存档不宜默认 192G

- **P 阶段。** E3 按行数线性外推（4.28 小时），算法正确。但 PCAP 解码与快照重建的成本取决于要解码的捕获字节数（72 份，8.32 GB），与查询行数无关。三设备与源侧共享大的 Active 捕获，所以 P 阶段可能不短。建议用 Job177891 的 P 阶段耗时除以当时解码的字节数，得到每字节成本，再估算这一阶段，写进资源方案。
- **内存。** 09-29 那次，192G 的申请超过了 node188 约 155G 的可分配上限，作业因此长时间排队，这对用户是实际成本。三设备的行数约为 177891 的 31%，177891 的批记账 MaxRSS 为 40.9 GiB。建议准备阶段的暂定档不超过约 150G，以能装进已知可分配的节点，再由有界资源探针确认；只有探针证明确实需要，才升到 192G。
- **异常流。** v3 复审时提过：范围外的每一帧都会写一行异常记录。三设备在共享大捕获上运行时，范围外的帧会很多。建议在新入口中改为范围外普通帧只记计数，只有带旧异常的帧才逐行记录，并在磁盘预算里留出余量。
