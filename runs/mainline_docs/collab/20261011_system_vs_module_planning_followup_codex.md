## 1. 零新增漏检明确作为整套系统验收门槛

新版 `a_regression_contract_outline.json` 将模块配对检查明确标为 `SYSTEM_ZERO_ADDED_ATTACK_MISSES`，角色为**未来完整系统必须通过的验收门槛**。

两个 A 池与 UNSW 共 3 池，分别检查 seed 27、127、227 和固定 ensemble，共 12 个配对格。每格按相同新基础头、相同源 CAL cut、相同 UID/标签计算：

`added_miss = count(label==1 AND new_head==1 AND new_full==0)`

任一格出现一条新增漏检，整套系统判 FAIL；即使总召回仍≥99%、另有攻击被救回，也不能抵消。缺配对结果、身份不一致或预期支持未验证时，不得记 PASS。原始整数计数是主判据，不用舍入后的加权差值代替。仍报告逐设备、协议和活动等分组。

原研究底线照旧；`OLD_LEVEL_PRESERVED` 仍只是旧 FULL 与新 FULL 的报告标记。当前 QUERY_TAIL 只检验基础头，其参考保护仍为 NOT_TESTED。这条未来系统门槛不回写当前头的判定，也只是在固定评价池上的经验验收，不是对所有未来攻击的保证。

## 3. 解码器身份与共享捕获的父特征回放

接受，单列 `three_device_replay_protocol.json`，作为下一版准备验收的必要条件，当前状态为**草案、未冻结、未实现、未回放**。

缓存键增加 TShark 版本/build 与可执行文件或发行物身份、实际命令及 56 个字段的顺序、重组相关偏好和有效偏好摘要、解析器/tokenizer/owner scope 代码身份。同时绑定 E3 数值环境、线程和批处理规则。

父运行已记录 TShark 4.6.6，但没有保存完整 effective preferences，原命令也没有显式重组开关。不能声称只凭版本号就已复原解析语义，更不能直接关闭 `ip.defragment`。新入口需记录自己的实际配置，并通过父输入/特征回放建立兼容证据。

7 个共享 Active 捕获的 SHA/大小已从父小清单绑定，合计 7,218,605,495 字节；本轮没有读取原始 PCAP。拟先登记 1,024 个父 UID：按捕获分层，每份 146 行，按固定捕获 SHA 顺序前两份各加 1 行；捕获内使用固定盐的 UID 哈希排序，不按标签、分数或是否易于通过选择。精确 UID 清单及父批次清单在真实回放前封存，现在仍为 PENDING。

回放需补上原批次布局：父 E3 按全 spool 的 `(protocol,width,bursts,uid)` 顺序形成至多 16 行的同 shape 批次，并非按捕获组批。只将抽出的 1,024 行重新组批，数值差异可能来自布局变化。因此要绑定父 `batch_id`、slot 和完整成员，用新入口重建被选行，再用已核验父 spool 的伴随输入补齐原批次。伴随行可能来自 7 捕获之外；不默认增加这些捕获的 PCAP 解码。实际回放前向行数待批次去重后确定，上限为 **16,384 行**，需单列到资源账目。

整个新入口仍需保留父 known-owner/required-owner 语义、完整前序时序和当前查询 token 证明，不能为了回放而直接缩成三设备 owner 范围。原始 RECENT E3 要求 shape、有限 float32 与每个元素位模式完全一致，以 `uint32` 视图或规范字节比较；普通 `allclose`，以及不能区分正负零的浮点相等，都不能冒充逐位验证。若保留 state26，另列状态列一致性检查，不代表恢复使用 STATE 头。

1024 行是固定样本的一致性证据，不是所有捕获、协议与 shape 的穷尽证明。新 wrapper 的范围隔离、异常处理及边界 shape 仍需合成验证；回放必须调用实际新数值路径，不能绕回旧入口制造通过。

**如果原父特征或 spool 不能恢复，真实父回放记 `PARENT_PARITY_UNAVAILABLE`，不能 PASS。** 合成一致性可支持继续开发，但不能替代这个真实数值条件。若最终需要重建整套缓存身份，应另立恢复/再验证协议，不能把新重建缓存当作原 gold 自动通过。

## 4. P 阶段、内存目标与范围外日志

### 4.1 P 按字节及扫描次数核算，当前不虚填秒/字节

已补入原作业的实际扫描口径：

| Job177891 的准备工作 | 逻辑读取字节 |
|---|---:|
| 原始文件身份校验，219 捕获 | 18,534,039,987 |
| 主 spool 解码一次 | 18,534,039,987 |
| 四捕获额外预检解码 | 7,685,995,896 |
| 解码累计 | **26,220,035,883** |
| 原始校验与解码合计 | **44,754,075,870** |

上述累计不是磁盘设备实际 I/O 计量，文件系统缓存也会影响成本。额外预检包含 active-00、active-01 和两份 UNSW 捕获。

现有 `target_probe.json` 的 12,604.7029 秒是到探针完成为止的**混合准备阶段累计**，含环境/身份检查、特殊预检、旧缓存审计、解码重建、SQLite 写盘和探针。没有独立解码 wall time，不能把它除以一次 PCAP 字节数当作纯解码速率，也不能拿包含 E3 的整个 P 阶段按字节外推。

新三设备已知单遍原始量为 8,323,214,117 字节。新版方案分别登记身份校验、主解码、额外预检和回放的扫描次数；解码秒/字节和 P 总时长暂为 null/PENDING。下一版 wrapper 按阶段及捕获记录 wall time、bytes、frames、扫描次数、输出和内存，再按同口径成本估算；状态构造与索引成本也需保留。4.28 小时仍只是旧 16×4 并行度下的纯 E3 条件参考。

### 4.2 优先不超过 150G，保留用户原先的 130G 条件

接受把新准备方案的优先目标改为 **≤150G**，不再默认申请 192G。但历史原文 `legacy_continuous_input_v2_memory_review_20260929.md:3` 写明：用户当时报告 node188 可申请约 155G，并要求**有把握峰值低于 130G 才出 150G 包**。155G 是当时的可用资源报告，未远程核实，不能写成现在已证实的节点硬上限。

新档位冻结前，需要覆盖父进程、多 E3 worker 同时加载、最大合法 shape、多 shape 分配器残留、SQLite/页缓存与合并临时量的可信资源预算，并说明 tree RSS/cgroup 计量范围与余量。旧 40.94 GiB 单项 MaxRSS、31% 行数或 33 行数值探针都不能代替这种证据。

必要时先在协议里登记降低 worker 并发；并发降低后重估 E3 时间，不能继续无条件引用 4.28 小时。证据不足时资源合同保持未冻结；不自动升到 192G、不自动重试、不修改当前 v2r1 的既定资源。未来模块本身的资源仍待实现后核算。

### 4.3 普通范围外帧可汇总，新旧异常均要保留

接受压缩范围外普通日志，但“只保留旧异常”需要收窄：只有**非固定 target、旧异常为空、当前事件仅为 `OUTSIDE_REQUIRED_OWNER`** 的普通帧可以只保留计数和增量 identity 摘要。

任何新异常（包括 `CAPTURE_REGRESSION_OUTSIDE_SCOPE`）、旧异常、target 或 context/namespace failure 都保留逐帧证据和原停止语义。逐帧 Contexts/旧审计更新仍执行，不以省日志为由跳过时序状态或范围审计。early/main 使用同一版本实现对账，日志 schema 另立版本，不宣称新的日志文件 SHA 与旧版相同。

这是下一版 wrapper 的设计要求，尚未改现有审计代码。实现时需验证缩减前后目标 token/特征、计数/摘要及异常停止行为一致，并为 SQLite、异常证据、回放伴随行和失败回传保留磁盘预算。
