## 0. 分工与原则

- **Claude**：定方案、定每一步的验收与停止规则、审查关键实现、解读结果。技术分歧由 Claude 拍板，并在 collab 中写明理由。
- **Codex**：按本文实现、运行，回传带 SHA 的证据。发现本文有错或不可行时，先在 collab 中指出，不得自行改变方向。
- **用户**：只决定研究目标与评价口径的取舍（见第 6 节），并授权云端运行。
- **不再做的事**：继续换检测头；扩大 λ 或 cap；D1 式整体抬阈值（已证实会丢攻击）；继续发展学习型入网模块（弱于 V3，归因 FAIL，保留为消融）。
- **主线系统固定为**：QUERY_TAIL 三 seed 集成 + V3 几何入网 + 原源 CAL 切点。后续每一步只改一个因素。

## 2. 三个可证伪的假设，分别对应上表的三块

- **H1（主要影响 A）：误报大多发生在新设备的观察期内。**
  - 观察期内的查询按现行规则只能用检测头的原判定，入网模块在结构上无法介入。
  - 这首先是评价口径问题（见第 6 节），而不是模型问题。
- **H2（B 的 6.99 个百分点）：单条长连接设备被“至少 2 个组件”规则挡在门外。**
  - 推测 Samsung 和 WEMO Switch 的 TCP 主要是少数持久的云连接。观察窗口内不足 2 个组件，于是之后这条连接上的所有数据包都不合格。
  - 而这些包很可能正是观察期内受信任连接的延续，是最强的正常证据。
- **H3（B 的 9.24 个百分点）：参考在“会话阶段/上下文”上太稀疏。**
  - 每个组件只取一个代表位置，每台设备最多 64 个点。
  - 距离按 `max(dz/2, dq)` 计算，当前包标志位只要与参考不同，dq 就至少约为 0.27。
  - 误报以 ACK/数据包为主，而参考多半不是同一阶段，导致零支持或支持偏弱。

## 3. 第一步：只读核查（约 1 天，不训练，不新增 E3）

在云端已有的 trace、决定与元数据上，对 QUERY_TAIL 集成 + V3、B2 计算以下三项。

**C1（检验 H1）：观察期口径**
- 两池分别统计观察窗口内的正常与攻击查询数，以及它们的权重质量。
- **窗口内是否有攻击查询必须报告。** 如果有，“观察期可信”的前提不成立，要单独说明。
- 计算“观察期后”口径的加权 FPR 与攻击召回。做法是：只保留窗口结束后的查询，按原“设备 → 活动 → 捕获 → 会话 → 行”层级重新归一化权重。池级和逐设备都要报告，并与全量口径并列。

**C2（检验 H2）：Samsung、WEMO Switch，以及所有“其他不合格”的 TCP 误报**
- 不合格原因码的分布：NO_REFERENCE_BANK、FEWER_THAN_TWO_LEGAL_COMPONENTS、PREBANK_HISTORY_HEAD_ONLY 等。
- 这些设备在观察窗口内的 TCP 组件数，以及可作为查询的位置数。
- 误报查询中，有多大比例（按条数和权重）的 component_id 在观察窗口内出现过，即属于“受信任连接的延续”。

**C3（检验 H3）：TP-Link、WEMO Motion、Netatmo 的合格误报**
- 对零支持和修正不足的误报，比较两种参考下的最近参考距离 d，并拆分为 dz 和 dq：
  - (a) 现有 B2 库；
  - (b) 密参考代理：B2 库加上同设备、同协议、在观察窗口内、已编码的全部 DEV 查询。这一步只用时间戳，不用标签。
- 再用 V3 原公式和原 λ 重算“假如用密参考”的支持度与修正。只看正常误报会有多少被修掉，以及攻击 TP 中有多少获得正支持。
- 同时报告：误报的当前包阶段，与其最近参考的阶段，两者是否一致。

C3 是诊断，不作为结果宣布。同时要把攻击的支持变化与正常的支持变化并列报告。

**判读与分支：**

| 结果 | 下一步 |
|---|---|
| C1 中 A 的观察期后 FPR 明显下降 | 交用户决定口径（第 6 节） |
| C2 中延续连接占误报权重多数 | 第二步加入“延续资格” |
| C3 中密参考让零支持和修正不足的误报大量获得足够修正，且攻击未获正支持 | 第二步加入密参考 |
| C2、C3 都不成立 | 跳到第四步（检测头侧），不再改参考 |

## 4. 第二步：密参考 + 延续资格（新版本，独立登记）

只改参考的构造与资格。V3 的距离、支持函数、scale 和 λ 选择程序都不变。

- **参考位置：**
  - 用观察窗口内同设备、同协议的全部合法查询位置。
  - 先用已编码的部分；不够时，再补编码窗口内位置，每个（设备，协议）上限 4,096 个。
  - 选取规则：按组件轮转，组件内按时间均匀分布，排序用固定盐的 SHA256(UID)。不看标签或分数。
- **资格：**
  - 原规则“至少 2 个不同组件”保留。
  - 新增延续资格：查询所属组件在观察窗口内出现过，且该组件在参考中至少有 8 个位置。
  - 攻击连接都是在窗口结束后新建的，所以不会因此获得资格。这一点必须用数据核实并报告。
- **源侧一致性：** 源 CAL 选 λ 时，源参考也按完全相同的规则构造，从已编码的 LEARN 早期窗口中取，不需要新的 E3。λ 由原保护程序重新选定，不手调。
- **对照**：同头、同切点、同查询，每格报告 3 个 seed 和集成。

  | 臂 | 内容 |
  |---|---|
  | R-B2 | 原库 |
  | R-DENSE | 只加密参考 |
  | R-CONT | 只加延续资格 |
  | R-DENSE+CONT | 两者都加 |
  | R-DENSE-WRONG | 等密度的错设备参考 |

- **验收：**
  - 原研究门槛：池加权 FPR ≤ 1%、每设备 ≤ 2%、攻击召回门槛；全量口径与观察期后口径都报告。
  - 零新增漏检整套门槛：3 池 × 4 个 suffix，任一格出现新增漏检即判 FAIL。
  - 自身参考与错设备参考的差异只作为“设备特异”主张的条件，不作为达标条件。
- **停止：** 身份、数值或资源异常即停，并保留现场；科学 FAIL 也必须完成全部对照。不按目标效果调整阈值、上限或规则后重跑。

## 5. 第四步（有条件）：检测头侧

只有在第二步之后，剩余误报以“任何合法参考都覆盖不到”为主时才做。依据第二步的残留分账，再在“主机级上下文”（先检验 H-c）和“增加源正常多样性”之间二选一，届时另立设计。

## 6. 需要用户决定的事（第一步结果出来后再问）

**观察期口径。** 新设备在采集参考的那两小时里，现行规则是照常用检测头告警，并把这些告警计入误报。可选的另一种做法是“学习模式”（Kitsune 等系统的惯例）：这段时间不告警，误报只统计观察期之后。代价是观察期内不提供攻击检测，论文中必须写明。

我的建议是两种口径都报告，主指标用“观察期后”，因为它衡量的才是入网方法本身。但这会改变评价总体，属于研究目标的取舍，由用户决定。没有 C1 的数字之前不做决定。
