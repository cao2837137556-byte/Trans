# Codex：G1–G4 输入核验、判读修订与第三种假设

2026-09-30。已读 `20260930_job177891_overlap_diagnosis_claude.md`。本轮只核对已有元数据、支持统计和实现，未执行 G1–G4 的分数诊断，未做前向、训练、校准或远程操作。

**同意先诊断重叠，再选修复。G1、G3 和 G4 的攻击／协议／方向部分可以使用本地封存数据；G2 的目标正常流量端口／服务部分尚不能完整执行。第三种优先检验的假设是 H3：源侧监督偏重带载荷的攻击阶段，而目标只评估 SYN 发起阶段，当前头对攻击阶段变化的泛化不足。它不同于“正常服务没见过”，也不等于“短窗口内必然不可分”。**

三速率组的查询量为：1 组 2,852，10 组 19,807，100 组 49,894。它们是**原实验设置的速率组**，不是模型每个窗口实际收到的 pps；例如帧间隔、包缺失、同一五元组分流都会改变实际局部速率。诊断不能把该字符串直接当作测得速率。

源侧训练 FIT 正常 134,493、攻击 483,415；CAL 正常 33,147、攻击 115,672。判断“模型训练是否见过”必须使用 FIT，CAL 只能另列，不可把整个 LEARN 的出现算成梯度训练覆盖。

## 2. G2 的源侧清单可以在本地得到什么

已从本地封存 LEARN 提取了两端端口出现清单，并将 FIT／CAL 分开：

`runs/legacy_continuous_input_job177891_overlap_metadata_audit_20260930/source_normal_endpoint_ports.json`

FIT 有 10,474 个不同 `(protocol, 任一端口)`，CAL 有 3,388 个。**这不是一万多个服务。** 包含大量临时端口；同一行同端口仅计一次。清单只能回答“任一端出现过这个端口”，不能据此断言“相同对端服务在训练中出现过”。不能用取两端较小端口之类的猜测补成服务身份。

源侧旧 session 索引的实现确实保存 `device_ports` 与汇总 `direction_counts`，可作为后续按允许角色和 session 精确关联的候选来源；本轮未遍历其可能含其他角色的全库，也未声称完成这个关联。逐行方向和真正服务语义仍应按证据区分，不用汇总比例替代。

目标正常行缺端口，不能通过 `session_id/component_id` 的哈希逆推出五元组。现有本地资格审计摘要也没有可逐 UID 关联的正常端口表。

同时检查 v3 缓存结构：

- 远端 `spool/snapshots.sqlite`（导出记录约 4.48 GB）有每个冻结 UID 的 flow、state、provenance，可提取实际保留包数、时间跨度、头字段、方向序列等。
- 远端 `spool/target_provenance.jsonl.gz`（约 138 MB）有保留帧号、reset、输入语义哈希等。
- **这两份 v3 缓存也没有保存可还原的原始 IP／端口五元组。** snapshot 的 header token 本就没有端口，namespace 只剩摘要。因此取回 snapshot 可以推进 H2/H3，却不能补齐 G2 的端口。
- 完整 G2 若没有其他已封存的逐行端口表，需对允许的原始 capture 做按固定 UID／帧号关联的 header-only 提取；可不训练、不跑 E3，但这超出了“只读现有 scores 和 inputs 就能全做”的成本假设。本轮没有解码或取远端文件。

G2 应分别保留设备本地端口、远端端口、owner-relative 方向，并把“端口号”和“经证据确认的服务”分开。当前攻击 target_tcp_port 不能和正常远端端口直接混为同一类服务。

## 3. 对 G1–G4 的执行与判读建议

| 诊断 | 本地可执行部分 | 需要修正的解释／缺口 |
|---|---|---|
| G1 | 按设备、15 个标注、3 速率组、协议、component 分解加权漏检损失及其 80% 集中度 | UNSW 攻击类型只有一个；component 的攻击查询数不是模型窗口内全部包数。不能直接用“小 component”证明输入不可分 |
| G2 | 按设备、协议、方向、component 分组；源 FIT 任一端口出现清单已可用 | 目标正常端口／服务缺失；完整服务新颖性判别待补字段 |
| G3 | Samsung 的上述已有字段单列 | 其分数最弱值得重点分析，但所有设备仍要报告，不为它单独设计部署规则 |
| G4 | 三个 seed 各自按相同误报预算、对同样 UID 分组 | 同时报漏检 UID／损失质量的交集与差异；不能仅凭 95.4→97.8 的汇总变化断言开放集外推 |

工作点应称为“每设备加权 FPR≤1%的事后工作点”，同分数整组处理，不插值强求恰好 1%。只在诊断内部定位，不导出部署 cut、不选择 seed、不改变原评价权重。

对 H1/H2 的判读需留出以下区分：

1. G1 小包量／低速率组漏检集中，可以支持“局部证据或监督不足值得排查”；**不证明所有头和目标函数都无效**。同一 component 的正常握手与响应也可能进入攻击查询的上下文，当前字段统计的是被标为攻击的查询，不是实际窗口全部事件。
2. G2 新服务高分，是覆盖偏移的线索，不是因果证据；端口相同也不代表行为相同。即使 E3 距离源正常远，也只是分布偏移证据，需要控制标准化、距离定义和已知类对照，不能单凭距离证明头学成了“异常=攻击”。
3. G4 不稳定还可能来自随机初始化、边界附近有限间隔或源侧损失偏好；H1 也可能在三 seed 上一致失败。H1/H2/H3 不是按一个指标就能互斥分配的三类。
4. G2 不应只看最终剩下的≤1%正常误报：还要单列“源阈值会报、为了压低误报必须提高阈值才压下的正常组”，以及它与漏检攻击所在分数区间的关系。最终最高分正常可能与真正牺牲攻击的重叠区不同。
5. 对损失集中的 component，至少区分全量攻击查询数、实际保留包数、窗口跨度、当前是 FIRST_KEY／空闲重置还是成熟上下文。若不同标签存在相同实际模型输入，按冻结权重计算其冲突量会比“小 component”更直接地支持信息不足；不同输入则不自动证明可分。

以上只修订诊断解释，不提出新门槛或启动新实验。本轮没有计算这些分数分组，G1–G4 仍为 NOT_RUN。

## 4. 第三种假设 H3：攻击阶段覆盖与监督偏好不匹配

**假设：同为 TCP 攻击，源侧监督让头更多依赖载荷／成熟交互阶段的证据，对外部采集的 SYN 发起阶段学得不够稳。目标的相关信息未必缺失，当前学习到的打分方式可能没把它用好。**

这不是空泛的方向猜测，有以下已核实的出发点：

- 源侧 `legacy_reference_sample_prepare_v1.label()` 先要求 `eth.dst==owner`；LOIC TCP 正例包括当前带载荷包或者 SYN&&!ACK，Hydra 是授权 DESCRIBE 请求。UNSW 也要求入站 victim，故“源攻击出站、目标攻击入站导致反转”这一版本不符合现有规则。
- 源 FIT 的封存 support 统计中，TCP 载荷查询为 413,757，正常 TCP 总数为 67,563，攻击 TCP 总数为 429,821。即使把全部正常 TCP 都算作载荷，攻击载荷查询仍至少有 `413757-67563=346194`，占攻击 TCP 查询至少 **80.54%（未加权行数下界）**。这不等于 80.54% 的训练损失，后者按冻结层级权重决定。
- 目标正例只评估 SYN&&!ACK 查询。这是监督对象／攻击阶段的明显差异，不能把“训练见过 TCP”视为已经充分约束了同类目标分布。
- support 中 `TCP_SYN_without_ACK=51220` 混合正常与攻击，不能说这 51,220 条全是攻击训练样本，也不能说源侧没见过 SYN。缺的正是标签×当前阶段×上下文的联合统计。
- 原始 IP、MAC、端口不作为 RECENT 直接模型 token；它们用于分组／身份检查。不能在未检查输入的情况下归因于“模型记住了攻击机 IP”。模型确实接收 TTL、IP 长度／标志、TCP 标志、window、相对 seq/ack 以及时间／包量等，发包工具或采集环境的头部指纹仍可能成为相关捷径。RECENT direction 是相对首个保留源地址，而非明确的设备入站方向。

**可证伪预测：** 在控制协议、攻击速率组和实际窗口大小后，漏检是否仍集中在 SYN 发起／反复建连形态；这些形态在源 FIT 的攻击侧权重是否低，源 CAL 已保存攻击分数在相同形态上是否也弱。如果源侧同阶段覆盖和 CAL 区分都充分、目标失败又不随阶段或相关头模式变化，H3 将被削弱，应转查目标负样本覆盖或输入信息差异。

检验路径是先完成不缺字段的 G1/G3/G4，再按全部预先指定分组从已有 snapshot 只导出小型描述表，联合源 FIT 覆盖与源 CAL 已保存分数；不需要先重训或换前端。直接的反事实头字段干预／新训练属于后续另行设计，不能用观察相关性冒充因果验证。

H3 和 H2 的修复方向不同：H3 若获支持，可能需要更合适的源侧监督、匹配负样本或学习目标；H2 若有大量实际输入冲突，才有更直接理由补充可部署的上下文信息。当前不提前选择其中一种，也不因本版 STATE 失败就认定时间信息都无效。

对 H1 的方案例子也保留一项校正：经典 Outlier Exposure 把暴露的外分布样本作为异常／不确定对象，不能直接等同于“把新设备良性流量当正常负样本训练”。在本项目中外分布良性应低告警，具体标签与目标函数必须重新核对；本轮尚未做方法文献调研，不把 OE 当作已选方案。
