# Claude 对 Job177891 结果的联合区分机制讨论

2026-09-30。依据：`legacy_continuous_input_job177891_result_20260930.md` 与 `legacy_continuous_input_job177891_result_20260930/verification_and_analysis.json`（按设备逐臂核对，未改文件）。约束：不直接重训，不用 DEV 标签调阈值。

**结论：同意 Codex 的判断（保留持续输入与 owner 隔离修复；RECENT 作为基线；暂停“状态分支 + 学习否决”）。建议下一步把“正常侧抑制”从学习否决器换成按设备、只用正常参考做的分位数校准（Kitsune/保形异常检测的成熟做法），先用只读诊断确认上限，再决定是否实现。**

## 1. 从结果读出的三个机制事实

**(a) RECENT 的问题是阈值整体偏移，排序没有坏。**
- UNSW 上 RECENT 的正常样本 margin 中位数为 -3.1，说明从源侧带来的阈值落在 UNSW 正常分布的中间。攻击样本 margin 的 10% 分位为 15.3，中位数为 84.3；正常样本的 90% 分位为 28.0，99% 分位为 47.8。
- 误报分散在全部 5 台设备，并不集中在某一台。加权 FPR：Samsung 11.5%，TP-Link 11.8%，Netatmo 28.6%，WEMO Switch 25.0%，WEMO Motion 29.4%。
- 事后排序上界（仅作诊断）：全局 1% FPR 时攻击召回 96.19%。CIC 侧也一样：RECENT 的 FPR 为 5.76%，没过 1%，而排序上界为 99.91%。
- 所以两个池子的主要问题都是**校准**。区分能力本身是有的。

**(b) 学习否决器是按“设备 × 协议”整段开关，不是逐条判别。**
- 以 WEMO Motion 的 TCP 为例：正确参考下攻击 0/14553、正常 21/16382；错误参考下攻击 0/14553、正常 23/16382。两者几乎相同。
- 它压下误报的设备（TP-Link、Netatmo、Motion）正好就是整段抹掉攻击的设备。Samsung 和 WEMO Switch 上它几乎不起作用：误报不降，漏检也不增。
- 所以它学到的是“这一类 (设备, 协议) 像源侧正常”，用的不是参考本身。这类结构没有保护攻击的约束，靠调门槛修不好，建议停用，不再修补。

**(c) 26 维状态降低了迁移能力。**
- 早期 6 条攻击查询：RECENT 6/6，RECENT_STATE 1/6。
- 三个 seed 的召回分别为 78.8%、90.1%、98.7%，很不稳定，符合捷径加协变量偏移的特征。
- 它对 UNSW 的误报几乎没有帮助：RECENT_STATE_RAW 的加权 FPR 为 17.7%，RECENT 为 21.3%。
- 按“不能大杂烩”的规则，它没有解决任何已证实的失败，所以从部署链中移除。只作为消融保留在报告里。

## 2. 提议的最小可证伪改动：按设备做参考分位数校准

部署链改为：**因果输入 → 冻结 E3 → RECENT 攻击头 margin → 按设备阈值 τ_d → 告警**。

- 删去学习否决器和状态分支。部署链只剩一个判别模块和一个校准步骤，每一步都可以单独消融。
- τ_d 取自目标设备正常参考窗口（登记数据）上 RECENT margin 的 (1-α) 分位数，并加有限样本保形修正（取第 ⌈(n+1)(1-α)⌉ 个值）：
  - 最终阈值为 τ_d = max(τ_src, 该分位数)。这样只会升高阈值，误报不会比现在多。
  - α 事先固定，例如 0.5%，不看 DEV。
  - 若 n < 1/α，退回 τ_src，并记为 `CAL_INSUFFICIENT`。
- 不训练，不使用 DEV 标签。阈值只依赖正常登记数据。这与 Kitsune 用部署初期的良性训练期最大 RMSE 定阈值，以及归纳保形异常检测（Laxhammar & Falkman 2015）是同一类方法，不是新造的。
- CIC 和 UNSW 使用同一规则，不是专为 UNSW 打的补丁。

**预期（写在运行前）：**
- 若参考窗口能代表设备的正常流量，每台设备的 FPR ≈ α。
- 攻击召回应接近下面 D1 算出的按设备上限。

**不通过时的解读：**
- **D1 上限低于 99%**：校准无法过门槛，问题出在表示层（E3 或攻击头）。需要另行讨论，而不是继续调校准。
- **D1 达标但 D2 显示参考与 DEV 正常分布偏移**：问题是非平稳，需要讨论参考窗口的选取协议。

## 3. 实现前的只读诊断（不训练，不改门槛）

请 Codex 先确认：每行的 RECENT margin（DEV 查询和参考窗口两部分）是否已保存在本地或超算缓存（`large_cache_retained_remote`）中。如果保存了，下面三项都可以在 CPU 上直接从缓存计算。

| 编号 | 内容 | 使用标签 | 作用 |
|---|---|---|---|
| D1 | 每台设备在加权 FPR 为 1% 时的 RECENT 攻击召回事后上限，含 CIC 各设备 | DEV 标签，仅作诊断，不产生 cut | 看按设备校准能否达到 99%/97%，决定走不走这条路 |
| D2 | 每台设备参考窗口 margin 的分位数与 DEV 正常 margin 分位数对比（1/10/50/90/99%），以及参考窗口相对 DEV 的时间位置 | 只用正常样本 | 检验平稳性，以及参考是否在时间上先于 DEV、互不重叠 |
| D3 | 按第 2 节规则、事先固定 α 得到的 τ_d，在 DEV 上评估一次，输出全部门槛指标 | 仅用于评估 | 如果 D1 与 D2 都支持，这就是正式检验；α 不得在看到结果后修改 |

- D3 须保留三组对照：RECENT 全局 τ_src、错误设备参考得到的 τ（检验是否真的依赖设备）、OLD_MATCHED 基线。
- 独立确认仍为 NOT_RUN。D3 即使通过也只是 DEV 层面的证据。

## 4. 需要 Codex 核对或回应的问题

1. 协议是否允许用目标设备的正常参考窗口定阈值。我理解现有设计已经把目标设备参考纳入范围，但需要确认它在时间上先于 DEV 查询、互不重叠，并且不含攻击。
2. 每行 margin 是否已保存。如果没有保存，只需重放攻击头前向，不涉及重训，算力与内存另估。
3. 如果 D1 上限就在 96% 左右，没有达到 99%，是否需要请用户重新审视 99% 的池级门槛是否合理。这是研究目标层面的取舍，由用户决定，我不预设结论。
4. 按“不能大杂烩”的规则，暂停的状态分支和学习否决器只保留为消融，不再作为部署候选。是否同意。

## 5. Claude 的独立看法（可能与 Codex 不同，供讨论、由用户裁决）

1. **参考校验器这条线建议整体放弃，不重新设计。** Codex 的建议是先弄清正确/错误参考为什么失效，再重新设计。我认为 (b) 已经回答了这个问题：否决器根本没有用上参考。论文里真正需要“参考”的地方，只有“用哪段正常数据定阈值”这一件事。把参考从一个学习模块降为一个校准数据来源，结构最简单，也最难被审稿人质疑。
2. **不必先做完文献调研再选方案。** D1 只需要已保存的分数，花几分钟算完就能判断校准路线能不能走通，应该放在最前面。文献调研和 D1 可以同时进行。
3. **（已按用户意见修正）这是待检验的假设，不是结论。** 目标仍然是修复迁移，现在不预设论文叙事。可检验的假设是：UNSW 上的失败主要来自阈值校准偏移，而不是表示能力不足。D1 就是用来检验这个假设的。
   - 若 D1 支持，修复路线是按设备校准。
   - 若 D1 不支持，修复重点转到表示层（E3 或攻击头），校准只作为辅助。
   无论哪种结果，都要把迁移修好之后再谈论文的立足点。
4. **证据量的风险。** UNSW 只有 5 台设备，每台只有一段攻击。即使 D3 通过，独立证据也只有约 5 个。独立确认集需要尽早确定，不要等到最后再找。
