## 4. ACK/UDP 与标签硬资格

正式确认必须含已证实的攻击方向 **TCP ACK=1、SYN=0** 和 **UDP**。TCP 细分 ACK-only、PSH+ACK、其他 ACK；SYN_NO_ACK、SYN+ACK、其他非守卫 TCP 均单列，不用大量 SYN 稀释非守卫风险。

保留发布方原标签，同时依官方发起者/受害者/时段/流规则分出直接攻击、受害者反向响应、背景和未知。反向 ACK 不是直接 ACK 攻击证据，不能改作正常参考。反射/放大按官方攻击链定义方向。

若只有整场景恶意标签而无法定位攻击向，最多支持场景压力结果，不能宣称严格 ACK/UDP 保护通过。ACK 或 UDP 缺失时完整主确认不合格，不先跑模型补证据。实际只有一类 ACK（例如 ACK-only 而无 PSH+ACK）时明确范围，不能外推为所有 TCP 行为。

正常流量同步报告 SYN_NO_ACK、ACK-only、PSH+ACK、UDP 和 idle/active/interaction，含真实连接发起/重试场景；不能仅凭 SYN 标志认定重传。

## 5. 指标与事先判断规则

**主要告警负荷指标为主视图 ensemble 逐样本 FPR**，并列逐样本召回、FP/FN/N；同时报告 full、四头、逐设备、协议、攻击事件/方向、守卫/非守卫及明确权重下的加权指标。池级目标 FPR≤2%、召回≥99%作为待检验目标，失败照实报告；所有设备≤2%是额外分账，不冒充已有保证。

当前冻结 metrics.py 只接受旧 pool 名称，且 A/B 权重层级不同。**不得把 CICIoMT 冒名填成 CIC_DEV。** 草案拟采用：正常按 device→logical capture→component、攻击按 device→official event→component 逐层均分，正常/攻击各自归一；protocol/flags/方向另做分层报告。该提案须由真实元数据核对 logical capture/official event 语义后，在评分前冻结为新 schema。分片不能平白变成独立 capture；缺失事件不能全填 UNKNOWN 让安全门空过。最终权重哈希公开，加权率不能代替逐样本负荷。

安全分账沿原相对 RAW 的累计撤警语义：四头、两视图均查每设备加权召回损失≤1pp、活动/可用事件≤5pp、RAW 召回低于99%的组零 TP 撤回；缺人口/标签记 `NOT_EVALUABLE`。另把 ACK/UDP 直接攻击的逐样本召回及 RAW→C5 新增 FN 单独作为必须报告的确认终点，不能只给池级数字。逐样本目标与加权保护门清楚区分。

一个新池是 2视图×4头=8份顶层保护报告，不照搬 A/B 两池的“16门”。正常告警不得因非负修正新增；出现则视为工程问题。对照均同 UID/标签/权重，不因支持不足排除困难查询。

报告每设备有效时长、独立日期/capture、攻击事件数、参考量、两组件/正支持/RAW回退覆盖和编码/距离/内存/耗时。置信区间若有足够独立块则预定按设备/捕获或事件成块计算；独立块不足时直接披露，不能将相邻包当独立样本或给加权率套普通 Wilson 区间。
