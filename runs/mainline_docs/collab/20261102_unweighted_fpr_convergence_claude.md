## 2. 执行顺序

**第 0 步：C4（180772）原验收。** 结果已取回，本地评价进行中。若 B 未加权 ≤2%，且全部保护门通过，就冻结 C4，第 1–3 步都不做，直接转外部确认。

**第 1 步：C4 天花板与撞车核查（Codex，本地只读，C4 验收后立即做，约 30 分钟）。** 输入是 C4 的保存数组（若 C4 未通过验收，用 C3 的，并注明）：
1. **分桶：** B 残留误报分为守卫、不合格、零支持、0 < 支持 < 所需支持、支持=1 仍误报五类，给出条数和权重。
2. **饱和上限：** 假设所有正支持都饱和到 1、零支持保持为 0，在 λ=0.25 下 B 的未加权 FPR。这是 D-D1 能达到的上限。
3. **撞车数：** 统计非守卫的攻击查询中，满足"support>0 且 原始裕度 < λ·scale"的条数，即在支持饱和时会被撤警的攻击。分别报告 A（开发诊断）和源 CAL；源 CAL 若缺逐行支持矩阵，先报告它的原始裕度分布，标明缺项。
4. **会话结构（为 D-D2 准备）：** 对 B 残留误报和 A 的非 SYN 攻击，报告同一 `session_id` 内因果前序查询的数量、时间间隔，以及 session 内是否跨越 SYN/FIN 边界。

**第 2 步：按第 1 步结果二选一（Claude 判读，规则先写死）。**
- 饱和上限 >2%：单包的 D-D1 理论上就到不了。这时零支持（主要是 Netatmo）是主因，转 D-D2，或者接受 C4 的结果，进入外部确认。
- 饱和上限 ≤2%，且撞车攻击数在源 CAL 和 A 上都不会让未加权召回 <99%、也不会触发任何既有保护门：做 **D-D1 单因素**。核形状 p 只由源 CAL 攻击保护和 HIST_DEV 正常决定，不在 A/B 上挑。
- 饱和上限 ≤2%，但撞车攻击多：单包机制不安全，转 D-D2，按第 1 节列出的三处缺口写成正式规格后再实现。

**第 3 步：唯一一次新机制 A/B 验收。** 采纳 Antigravity 的硬顶：180772 之后，A/B 上最多再做一次新机制验收，无论成败，之后冻结 A/B 开发线，转外部确认（CICIoMT2024 等）和论文。理由：A/B 已反复使用，再多迭代，只会让结果更像是针对这两个池调出来的。

## 3. 不变的约束

- 口径按讨论稿第 0 节和第 4 节：未加权池 FPR ≤2%、未加权召回 ≥99%；加权指标及全部既有保护门（逐设备 ≤1pp、活动/annotation ≤5pp、低基线零撤警）仍一票否决。另外并列报告逐设备未加权的宏平均，防止 Eufy 的体量冲淡 A 池比率。
- B 的攻击全部命中 SYN 守卫，因此不能用 B 为任何非 SYN 机制做攻击安全背书。安全证据只来自源 CAL、A（开发诊断）和未来的外部数据。
- λ=0.25、cut、scale、C2 守卫、几何半径都不动。

## 4. 用户决定（2026-11-02），修订第 2 节第 3 步

用户的意见：先把 A/B 上的结果做漂亮，再找合适的外部数据集测试；B 从未参与训练。
