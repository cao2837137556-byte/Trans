## 1. 结论与方向优先级

这次证据不支持把两台设备的困难正常一概称为“源侧从未见过”。在当前 V3 度量下，抽样误报都能在源正常中找到半径内近邻；同时源攻击也几乎都能提供半径内近邻。**有价值的方向是检验表示／判别边界／校准，而不能由“附近有正常”直接推出扩大撤警范围。** 主机上下文 S-CTX 值得做最小源侧对照，但本轮没有证明它有效，更没有得到新的 A/B FPR。

建议顺序：先按登记完成两折 S-BASE 的 S0 门槛，再做 S-CTX；覆盖剂量两格要先解决下述控制退化。场地级参考保留为待议设置，因为其他 B 设备参考对 FP 和 TN 都近，而且集合更大；当前证据不足以直接推进此设置。完整密参考第二步仍按既有独立计划等待授权，本轮不替代它。

## 5. 执行卡发现的两个实质问题

1. **S-CNT− 不是简单哈希取相同行数就能匹配权重。** 已冻结逐设备、删前精确权重分层的候选，匹配行数与有理数质量；但 SimCam 必然删除与 S-COV− 相同的 LAN_PHOTO 24 行。其 24 行是唯一最重的 24 行：12×1/162＋12×1/324=1/9，其他活动最大单行仅 1/378。任何保留至少一行该活动的同数量删除都达不到 1/9。这个结论针对**逐设备**严格匹配候选，不证明 r1 若采用折级总匹配也无解。需 Claude 明确匹配层级与退化处理，不能偷偷换盐、换 activity 或放宽质量后继续宣称干净对照。
2. **源侧没有已核实的 rate=1/10/100 标签。** 全部 766,727 行（其中攻击 599,087）和 33 个攻击 capture 的两份 catalog 均无速率字段。原攻击 README 明确每攻击重复三次，因此文件名 `_1/_2/_3` 是重复编号。现有攻击活动为 TCP 531,950、UDP 66,453、Hydra 684 行。分速率检出在本轮源对照应标记不可评，报告源攻击类型/capture 的条件召回；后续 B 的速率分组保留，不能借 B 来选择源方案。详细字段审计见 [control_audit/RESULT.json](../../diagnostics_step4_source_controls_v1_20261026/control_audit/RESULT.json)。

其余待明确的 S0 三 seed 聚合、每折更新数解释和删样采样日程在执行卡列出。现有生产 trainer 固定 617,908 FIT 和 782 维，不能直接套参数启动本对照；本次交付是绑定和执行准备，不是完成的训练 runner。
