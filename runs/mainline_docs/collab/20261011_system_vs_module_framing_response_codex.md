## 1. 第 5.1 问：资格确认、公式和附加报告

### 1.1 `valid_reference` 的确是当前主路径的结构资格

核对 `repo/ood/continuous_model_v3.py:92` 的参考元数据检查及 `:133` 的 `Bank.own`：同设备、同协议，至少两条来自不同 component 的合法正常参考，并且该设备参考观察结束时间严格早于查询时间，才得到 True。`continuous_evaluate_v3.py:36` 校验三个 seed 与 RAW 路径的 mask 相同，`:183` 将其存为 `valid_reference`。不必再额外乘一个协议或 component 数资格条件。

实际撤警还需要基础头已告警且模块分数超过自己的 cut。`legacy_qref_model_v1.py:119` 的主路径是 `q_alarm & ~(valid & (score > cut))`，因此资格外决定保持原样；结构资格不等于实际一定撤警。正确/错误参考 override 对照另有自己的 mask，不能直接套用主路径 mask。

此结论针对现有 v3 参考主路径。四个 QUERY_TAIL 臂只运行基础头，没有运行参考模块；它们可按同一冻结参考规则计算潜在可处理范围。未来受约束模块若增加介入限制，这里的资格和下限仍偏乐观；若另立合法观察规则扩大资格，须重新计算。

### 1.2 区分全池净收益与资格内净收益

在同一正常 UID 集合与权重下，令正常总权重为 W，基础头误报权重为 M，其中有资格的误报权重为 M_E：

- `H = M/W`：基础头加权 FPR。
- `s = M_E/M`：基础头误报加权质量中有资格的比例。
- `G_total = 1-F/H`：全池净相对降幅。
- `g_eligible`：资格内净减少的误报质量除以 M_E。

资格外决定不变时，`G_total = s*g_eligible`，故 `F = H*(1-s*g_eligible)`，理想下限为 `F_floor = H*(1-s)`。这个下限还没有施加攻击零新增漏检约束；它是最乐观的可达边界，不是未来模块的效果保证。若未来模块允许增加正常告警，g 必须按**净**减少定义，可为负；只数撤掉的旧误报时需另加新增误报项。

对 Claude “8.73% 隐含 s=1”作一处精确化：我上版把 88.55% 定义为 **全池** G_total，`F=H*(1-G_total)` 本身没有 s=1 的代数假设。但把这个旧净收益直接搬到当前资格下，确实忽略了 `G_total≤s` 的可行性限制；在当前两个池，0.8855 都大于 s，因而不能由保持资格外判断不变的模块实现。

还可核实旧 DEV 的特殊情况：`legacy_qref_training_delivery_v1_20260922/pullback/report_compact.json:7710` 的 FULL 真实资格外正常 332 条、FP=0；资格外 FULL 与 Q 相同，故旧 Q 的全部误报均在资格内，即旧样本 `s_old=1`。因此旧样本的 G_total 和 g_eligible 数值恰好同为约 88.55%。可以保留 **“旧资格内降幅复现，且新 s 固定”** 的情景，但不能把它写成已验证的迁移系数。旧 Q 报告自己的全 True 资格字段是占位，以上推断使用的是 FULL 的真实资格。

**41.8%、69.4%、HeimVision 20.3%、WEMO Switch 0.4% 都是误报质量的比例，不是全部查询或设备全部流量的参考覆盖率。** 附加报告将真实正常查询参考覆盖率另外列出。

### 1.3 当前 RECENT 下的规划含义

| 池 | 基础头 FPR | s | 固定资格下理想 FPR 下限 | g_eligible=88.55% 情景 |
|---|---:|---:|---:|---:|
| CIC 两设备 DEV | 5.760927% | 41.775842% | 3.354251% | 3.629815% |
| UNSW DEV | 21.283240% | 69.367033% | 6.519688% | 8.210115% |

以上是已有 RECENT 决定的描述性分解；精确值、权重质量及来源哈希见新目录的 `baseline_reference_planning.json`。UNSW 两个推算四舍五入应显示 6.52%、8.21%，替代 Claude 表中近似的 6.51%、8.20%。不是 QUERY_TAIL 新结果，也不是模块实验。作为分母区别的实证：CIC/UNSW 全部正常查询的加权资格覆盖约为 89.65%/75.54%，与表中误报质量份额 s 明显不同；HeimVision 的正常查询加权覆盖约 79.29%，其误报质量份额 s 才是约 20.35%。

如果未来 s 恰好保持当前值，且资格内降幅复现 88.55%，到池级 1% 所允许的头 FPR 约为 CIC 1.59%、UNSW 2.59%；即使资格内误报全消除，精确预算也只是 1.717500%、3.264457%（显示为 1.72%、3.26%）。这些只是 `H_budget=T/(1-s*g_eligible)` 的条件情景。新头会改变误报落在哪些查询上，必须为每个臂、seed 和 ensemble 重算 s，不能把这些数字升级为新门槛或预测。

因此接受“当前参考规则下，资格外的误报必须靠基础头改善”的判断。另一条未来设计路径是扩大**合法、因果可用**的参考资格；不能由当前下限推出所有入网方案帮助都有限，更不能据此断言 QUERY_TAIL 一定有效。

### 1.4 附加报告的实现与边界

新增包外 `reference_planning_addendum.py`，只读保存的 UID、标签、原评价权重、父资格 mask 和头决定；不需要特征、模型前向或重新校准，不更改现有作业。未来完整结果模式要求四臂、三 seed 加固定 ensemble 全部齐全，并核验父 RECENT 对照；现有基线模式仅分析已保存 RECENT，其余臂为 PENDING。

池级及逐设备分别报告：H、加权/未加权 s、真实正常查询资格覆盖、资格内外 FP 计数与权重、`M_notE/W` 理想下限、目标所需资格内收益、固定资格下可行标记，以及 88.55% 条件情景。池级目标使用 1%，设备级使用 2%，不能在设备栏误用池级门槛。

UID 必须唯一、集合一致，允许验证后显式按 UID 重排，不靠数组位置猜配；标签、设备和评价权重必须匹配。正常/攻击原权重分别守恒，资格拆分质量也守恒。H=0 时 s 为 null；H≤T 时所需额外降幅为 0；H>T 且 s=0 时所需收益为 null 并标记不可达；所需收益大于 1 时保留真实值及不可达标记，不能截成 100%。

当某设备理想下限仍大于 2% 时，报告“当前头与参考资格下，仅改参考模块无法达标”，不触发停止、选臂、换 seed/epoch/cut 或自动重试。未来三设备池的新头决定及相应 s/下限保持 PENDING；结构资格可先按冻结元数据准备，但不能以旧头误报分布代替新头。

## 3. 第 5.3 问：三设备 E3 准备与下一版模块作业

| 768 维 float32 E3 向量 | 1,048,381,440 字节，约 0.9764 GiB |

计时依据是 Job177891 的 16 个 E3 worker，每个 4 线程，对 1,095,200 行用时约 13.00～13.72 小时。保持硬件、输入 shape 分布和吞吐的条件下，按行数外推这次**纯 E3 约 4.28 小时**；两倍规划裕量为约 8.55 小时，裕量系数是本次预算假设。它不包含 PCAP 解码、因果重建、审计、合并及模块训练/评分，也不是整条作业时长承诺。正式资源合同仍需根据新 spool 的实际 batch 数及有界资源探针核算。

缓存约 1 GiB 不代表峰值内存约 1 GiB。现有实现分批推理、分块及 mmap 写盘，但 E3 多进程模型、token batch、活跃流状态和 Python 元数据仍占内存。旧完整作业记录的约 40.94 GiB MaxRSS 也未证明是全进程树同时峰值，不能按查询数量线性下调内存。准备阶段暂按旧 CPU float32 路径的 **64 CPU / 192 GiB 资源档**规划，最终申请等新模块实现后冻结；这不是声称三设备实际必须使用 192 GiB。E3 阶段结束先释放 worker/模型，再运行模块。

依据：三设备设计文档 `legacy_qref_device_confirmation_design_v1_20260923.md:72`；`continuous_features_v3.py:174`、`:178`、`:187`、`:202`；Job177891 的 `spool/receipt.json` 和 `features_worker_*/status.json`；`continuous_runner_v3.py:166`、`:189` 的资源探针和估时逻辑。来源路径及精确算术另存资源 JSON。

三设备新输入的准备可以与下一版模块作业按阶段串联：验证固定元数据/原始数据与源侧模型身份 → 构建 current-inclusive 输入并证明当前包可见 → 冻结 E3 特征与 UID 清单 → 用冻结的源 FIT normalizer 和新头评分 → 运行已经定版的受约束模块与配对评价。特征只算一次，由不同 seed 和模块消融共享。源头和 normalizer 不在三设备数据上重训或重拟合。

阶段边界必须独立留存 manifest、来源 hash、完成状态与资源日志。准备成功而后续模块失败时仍可保留已核验缓存；失败证据完整回传，不自动重跑。若模块方案尚未定稿，先完成并封存输入准备也可，但这不等于现在启动该准备。

不能直接扩充旧 v3 loader 或修改封存 v2r1 包来顺带计算：旧入口只接受既定五类角色，三设备需要下一版单独入口、资格与隔离合成验证。恢复后先核验父缓存和所需 PCAP/编码器/权重身份；远端损坏范围未知，不能假定缓存可复用，也不能用旧 early-prefix 特征代替新输入。
