### 2.2 D-A 的最小、可复核口径

本地可用 C3 `output/ab/{CIC_DEV,UNSW_DEV}/DECISIONS.npz`，联接原冻结查询元数据、窗口参考和 D2 取回的历史 `references.jsonl.gz`；HeimVision 还须并入 C3 新增参考。统计应分 **窗口库 / 历史新增库 / 实际合库**，同时列所有正常残留与所有攻击，保留 UID、原主视图权重和 owner 映射。

交集只能当“这条路最多触及多少”的覆盖上限。历史大量出现的判据若含次数、天数或服务角色阈值，尚未注册；这一轮可列分布，不能临时挑门槛后宣称白名单安全。

旧 C2b 的 **B broad 43,487 条、60% 攻击权重相交**成立，但有两个限定：

- 它是 **去 IP 的 broad `(owner, 对端端口, L4)`** 与旧两小时窗口服务的交集；不是 strict 四元服务键，也不是本次历史合库。
- **相交不等于实际新增漏报。** 保留 C2 后，这些 B 攻击仍走 RAW。它揭示了身份信任可能覆盖攻击，不能写成“当前方案已漏掉 60%”。

旧 B 元数据缺端点时，C2b 已逐包核验并保存 `UNSW_DEV_joined_selected_rows.jsonl.gz`；这批材料只覆盖当时登记的目标块及全部攻击。当前残留若不在其中，须标 `UNKNOWN_ENDPOINT` 并计数；不自动重扫原包补齐。对严格历史服务交集，若缺物理方向或历史 owner 映射，结论应为部分可核查，不能把未知行算作 0 交集。

因此，我支持做 D-A 的便宜覆盖审计，**不支持先把 D-A 放在第一执行顺位**。也不接受仅凭“跨年临时端口会变”就断言历史精确交集必为零；应以实际身份映射后的清单为准。

### 2.3 D-B 要拆成两个不同的数学问题

**固定支持敏感性：** 对非守卫行按保存的 `raw`、`support=s`、每头 `scale` 重算 `raw_j − λ·scale_j·s`；守卫行始终保持 RAW。集成按原三头均值和原 cut，比较符号沿原严格规则。报告每个 λ 的正常 FP、相对 C3 修复/新增 FP，以及攻击总 FN、相对 RAW 新撤警、相对 C3 新增 FN，按 SYN 守卫/非守卫拆分。

**support=1 理想上界：** 这是另一张 oracle 表，回答“只受修正幅度限制最多能修多少”。它不等于固定保存 support 的结果，不能把二者都称为“理想可修数”而混算。既有 844 条结论属于这张表。

本地 A/B 数组足以做第一张表：两份 C3 `DECISIONS.npz` 分别有 179,886 / 148,316 行，保存了 `uid/raw_logits/support/guard/base/corrected/eligible`；UID 联接后取原主视图，不能把 NPZ 全部行数当主视图分母。可以同时检查四头/全部旧保护组。新 λ 不在生产 core 的注册网格内，应由隔离的描述性算术脚本计算，**不修改 `LAMBDAS`、cuts 或生产代码来绕开合同**。Antigravity 回复已给出若干 C3 λ 重放数字，但本轮未独立复现其候选计算，不能在本回执中把这些新数字盖章为已独审。

源侧则要分清不同含义的“支持”：

- 180228 G0/G1 CAL 保存的 `Q/N/C_support` 是另一学习分支及 donor roster 的支持，**不能冒充固定 V3 几何/密库支持**。
- 旧 `source_actual_trace.npz` 的 logits/delta 也不是可直接替用的 V3 全 donor 支持矩阵。
- 179602 证明密库 CAL 做过，但仅有摘要、候选选择和数组哈希，不能从哈希反推出逐行数值，也不能从一个 λ 的最终选择反推出新 λ 的攻击撤警。

4,728 点的 `science/encode/banks/SOURCE_REFS/bank.npz` 和参考元数据也已在上述 179602 本地取回目录，分别含 E3/q14 与身份信息；这里缺的是逐行支持重放材料，**不是必须重新编码或必须再上云**。若未来授权，可能只需用既有特征做有界本地距离重建，但那已超出“仅重用保存 support、零新增距离”的本次评估范围。

如后续取得身份可核验的同版本矩阵，源重放须沿原“全部合法 donor 新增 FN UID 的并集”保护，而非只算自己的正常库；同时联接同 UID 的 q14 才能可靠拆分 SYN/非 SYN。现阶段可做 CAL 原始攻击组成和 margin 描述，**不能交付完整的密库新 λ 撤警表**。目标历史参考扩充也不会自动进入 LEARN 的同设备参考库，不能用源库旧 PASS 证明目标历史支持下的未知攻击安全。

## 3. 回答问题三：有没有更好的第四方向

**有值得保留的第四假说，但目前没有已证明安全、可直接执行且保证 2% 的第四方案。** 我更愿意先把它限定为单项 **D-D：有界支持函数的源侧校准**，对应 Antigravity 提案中的 D-D1；不立即叠加会话均值和设备半径扩张。

### 3.1 单项假说、最小证据和停止条件

- **假说：** 若 C4 后残留主要有正支持、却落在线性衰减的中段，问题可能在支持到修正的映射，而非 λ 上限。可研究 `g_p(s)=1−(1−s)^p` 等预注册单调映射，保持 `g(0)=0`、`0≤g≤1`、λ=.25、C2 和双组件资格不变。
- **最小证据：** 先等 C4 原验收，分清守卫/不合格/零支持/正支持不足/即使满支持也不足。正支持映射可用保存 support 做零距离重放；零支持不能据截断后的 0 反推出距离，更不能被这种核自动救回。先检查“所有合法正支持都饱和”的覆盖上限；若仍到不了池 2%，单独这项不能达标，直接记录，不叠规则凑数。
- **定参及对照：** 固定 p 网格与排序只允许由同版本源 CAL 攻击保护和预部署 HIST_DEV 决定；需要补齐前述源矩阵材料。对照仅 C4 vs C4+映射，保留全部四头门，不从 A/B 的最佳成绩挑 p。
- **停止：** C4 本身达标且保护通过则不启动。源侧不能区分候选、合法保护资产不足、或锁定后唯一验收触门，就不晋升。保持幅度上限不等于自动保持攻击安全：提升支持同样会增加 ACK/UDP 撤警。

这只是比 D-A 无条件身份信任、D-B 直接抬 cap 更值得先验证的结构假说。若 C4 残留主要是零支持，现有证据还不足以决定应改正常半径、表征还是数据覆盖；不能提前承诺它优于其他方向。

### 3.2 对 Antigravity“软核 + 会话因果聚合”的具体意见

方向有价值，但尚不能接受其整套方案“已收敛、最干净”的结论，也不接收其 A/B 候选成绩为本轮独审结果。至少有三处输入/安全合同需补齐：

1. **现有 `session_id` 不等于严格的单次 TCP 连接。** `constrained_onboarding_reference_v2.py` 明确校验 `digest([owner,capture_id,canonical_key])`；没有握手生命周期或 idle timeout 分段。UDP 更无天然连接。直接把它称为“绝不跨连接”的窗口会过度承诺。
2. **保存查询是采样序列，不是连续逐包流。** “同 session 其他包已正常”可能含未来包；只有逐行因果前缀的重放才可用于可部署机制。W=5 个保存查询不等于 5 个连续原包，也没有固定秒数。需明确到达顺序、冷启动、缺包、重传/复用、窗口最大时长和即时报警延迟；不能把完整 session 统计当因果证据。
3. **单包 cap 不会自动约束聚合后的当前分数变化。** 虽然每个输入 logit 的参考修正仍≤λ·scale，历史均值还可能把当前高异常值压低更多。正常长连接后插入 ACK/UDP 攻击恰是必须保护的情景。强异常直通阈值也是新超参，不能由 A/B 挑选；合成尾插测试可检工程行为，不能替代真实未消费攻击验证。

此外，生产 core 的 `second_joint` 是对每个参考先取 z/q 的最大归一化距离，再在不同组件间取第二值；**不能用独立 `second_dz`、`second_dq` 的最大值替代**。设备半径重标定若改变这个联合排序，需要真实联合距离信息；它不是有截断 support 就能零距离完整完成的附加项。

因此我的排序是：**先拿 C4 已注册结果；若仍不达标，先完成有明确缺项的 D-A/D-B 诊断，再由源侧材料决定单项机制。** 不将 D-A 当成预定主路线；不以“1.13% 下界”为由直接抬 λ；也不把软核、扩半径、时间聚合三项捆成唯一下一步。A/B 持续标记 `CONSUMED_DEVELOPMENT_DIAGNOSTIC_ONLY`，独立外部确认依旧不可替代。
