# 同服务正常登录：为什么 207 条连接全部报警

正式批次 `formal_20261122_402788` 的两小时正常库有 4,096 条参考、393 个同服务组件。用评价请求的原帧顺序对齐 UID、TCP 连接及认证结果后，从 `evaluation/DECISIONS.npz` 复算了 288 行配对表的请求数、连接数、原始误报、修正后误报及撤回数。45 个清单文件的 SHA-256 均一致。以下分析只涉及这次受控虚拟服务的合法行为，输错密码后重试也属于正常。[正式验收](20261122_paper04_same_service_formal_acceptance_codex.md)

**基础分数和扣分上限。** 对每个请求取三种子 RAW 平均分减原集成阈值，得到它高出告警线的分数。243 个正常请求中，214 个高出的分数严格大于原 v12 最大集成扣分 30.2243423462。该 214 个请求的 UID 集合恰好等于原 CCNR 最终误报的集合；每条评价连接至少含其中一个请求。因此在现有分数、阈值及扣分上限下，即使给满正常支持，连接误报数也至少为 207/207。该结论解释了本批样本上的判决；基础头为何给这个服务如此高的分数，仍是独立问题。

**相对握手的额外代价。** 原 CCNR 和 R2＋U1 都撤回了其余 29 个请求的误报，相对握手版本撤回了 6 个。差额 23 个全部是同一 TCP 连接内首次输错后再次提交且认证成功的请求：共 36 个此类成功请求，原 CCNR 误报 7 个，相对握手版本误报 30 个。对这 23 个新增误报，4 个在相对握手配置下不足两个相容组件，19 个仍有两个相容组件但扣分不足。频繁合法重连组的 51 个请求全部高于最大扣分额度，四组对它们都报警，现有四档未显示能够区分方案的误报拐点。[配对表](../../p4_login_formal_v1_20261121/received/formal_20261122_402788/PAIRED.csv)

复核使用 D 盘批次的 `evaluation/ALIGNMENT.jsonl`、`evaluation/DECISIONS.npz`、`QUICK_CHECK.json` 与冻结的逐头扣分尺度。额外误报由“相对握手有警且原 CCNR 无警”的请求逐一绑定到认证结果。后续宜单独核查基础头在同端点的判别与校准；这批正常样本能评价误报，攻击保留还需同端点独立带标签的攻击记录。
