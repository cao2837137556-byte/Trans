## 3. G2：高分正常是什么流量

按**当前查询包**的报头状态分类；分类不等于整个模型窗口的内容。标志优先级为 RST、FIN、SYN/ACK、带数据、纯ACK，UDP另列，不据此改模型规则。

| 当前正常包类型 | 正常查询数 | ≤1%事后工作点剩余误报行 | 占剩余加权误报 |
|---|---:|---:|---:|
| ACK、无数据 | 20,077 | 636 | 53.21% |
| 带数据 | 27,424 | 695 | 37.17% |
| FIN | 2,025 | 28 | 6.40% |
| UDP | 22,138 | 109 | 3.22% |
| RST | 870 | 0 | 0 |
| SYN+ACK | 1,626 | 0 | 0 |
| SYN、无ACK | 1,603 | 0 | 0 |

**ACK／数据包合计90.38%的剩余加权误报。** 在原源阈值下，ACK／数据包也占75.04%的加权误报；全部1,603条正常 SYN 查询在原源阈值和事后工作点都没有误报。

因而当前不能把重叠简单描述成“正常 SYN 与攻击 SYN 全部混在一起”。更值得问的是：为什么一些正常数据／确认通信获得了高于部分攻击 SYN 的分数，以及攻击头是否学到了能够跨通信阶段泛化的证据。

这不是写死“SYN报攻击、ACK放行”的理由。源侧攻击本来包括载荷阶段，CIC_DEV还有 TCP／UDP／HTTP 攻击；这些都必须继续保住。只按当前 TCP 标志放行会引入严重的新漏检。

### 端口覆盖能支持多少 H1

端口按报头明确分为设备本地端口、远端端口和方向。仅把实际远端 `(protocol,port)` 与源 FIT 正常任一端口清单比较：

| 覆盖情况 | 正常权重占比 | 原阈值组内加权FPR | 事后工作点组内加权FPR |
|---|---:|---:|---:|
| 源FIT任一端没有这个协议／端口 | 55.81% | 24.87% | 1.19% |
| 源FIT任一端出现过 | 44.19% | 16.76% | 0.70% |

缺覆盖组占原阈值误报65.21%、事后剩余误报67.99%，支持继续关注覆盖偏移；但不是“所有错误来自没见过的服务”。源 FIT 明确出现过 TCP443、TCP80、UDP1900；目标的一些高分正常也在这些端口。反之，远端临时端口缺失不等于新服务。

端口不直接进入 RECENT token；当前分析不能证明模型“学错端口”。协议／端口最多是行为与训练覆盖的定位线索。应用层服务身份未验证，不把端口443直接标成某种视频业务，也没有拿目标 DEV 正常行加入训练。

Samsung 尤其值得注意：按加权口径，高贡献误报包含本地49152端口的短正常 component；同一个49152也是它被攻击的目标端口。单靠服务白名单无法可靠区分正常与攻击。该设备仍有其他正常通信误报，不能为它定制一个端口例外。

## 4. G4：三个 seed 是不是只差运气

在各自相同的事后误报预算下，三个 seed 的 UNSW 攻击检出为95.4004%、96.2210%、97.7790%。

- 三 seed 都漏的攻击有1,169行，占整个冻结攻击指标 **2.2040个百分点**。这是具体工作点下的共同失误，不是对所有集成方法的数学上界。
- Samsung 三 seed 的攻击检出分别84.8206%、88.9470%、93.1607%，均是最差设备；分别占该 seed 全部加权攻击损失66.00%、58.50%、61.59%。
- 漏检并非完全相同：三 seed 漏检并集2,723行，交并集加权比45.77%。存在不稳定部分，同时也有稳定的失败群体。

结论：不支持靠换 seed 或挑最好 seed 来替代机制修复，也不能单凭 seed 差异把 H1 当成已证明的根因。

## 5. CIC 对照与三个假设的当前判定

CIC 在同一每设备≤1%事后条件下，加权攻击检出99.9437%；95条漏检都来自 HeimVision 的TCP查询，Eufy全部保住。CIC原本的较好分离能力仍在，修复必须保留这个回归约束。

| 假设 | 本轮证据 | 判定 |
|---|---|---|
| H1 外部正常行为覆盖不足 | 缺端口覆盖组更易误报，但出现过的端口也有误报；端口不是服务或模型直接输入 | 有线索，未证明；只补“新服务”不够 |
| H2 短窗口在低速率下信息不足 | 低速率更弱，早期样例难；但5个长component、83.57%损失在≥60秒，不能归结为单包／启动期 | 简单版本不获支持；是否存在实际模型输入冲突尚未知 |
| H3 阶段监督／判别证据不匹配 | 目标攻击都是SYN；主要高分正常却是ACK／数据；源FIT攻击TCP中载荷查询下界80.54%（未加权） | 作为优先修复假设，仍需源侧联合统计；不是已证明的因果根源 |

H3也可能包含窗口平均表示没有突出当前查询证据，或源侧目标未约束跨行为阶段的相对分数。当前记录不把这两点当成确认结论。

## 6. 下一步的具体修复方向与边界

**首选方向：保留已修好的 RECENT 因果输入与 E3，围绕同一个攻击头设计“当前查询与过去上下文相结合的攻击证据学习”，同时压低困难正常 ACK／数据通信的分数、保持 SYN及载荷等不同攻击阶段的分数。** 暂不再改设备阈值，不恢复旧否决器，也不预定换整个前端。

这需要在正式设计时核对三件具体事项，而不是继续扫超参：

1. 源 FIT 中 SYN攻击、载荷攻击、正常ACK／载荷的**实际冻结权重**和上下文覆盖。前次80.54%是原始行数下界，不能据此直接决定重新加权。
2. 当前768维平均表示是否丢弱了本次查询的阶段证据；若需补当前包信息，只使用截至当前可观测的字段／上下文，仍输出一个攻击分数，不增加端口白名单或一层放行器。
3. 选择有文献依据的匹配对比／低误报区排序学习方式，用合法训练侧样本约束正常与攻击的相对分数。目标DEV逐行标签只用于本次诊断，不能直接挑这些漏检／误报行塞进训练；若今后使用入网正常参考，另行明确其训练或校准用途。

正式结构、损失、对照和资源尚未冻结，也没有宣布新学习机制已实现。下一阶段是针对这些证据的修复设计／文献核对，随后才是一次明确的实现与训练对照。若源侧联合统计或实际输入冲突证据推翻首选假设，应据此更改设计，不硬走一条路线。

现有远端 `spool/snapshots.sqlite` 足以只读导出源 FIT/CAL及目标窗口的小型描述统计，不需要新E3或重训；本轮没有远程读取它。未获得全量实际窗口统计，不能声称已经排除所有输入信息问题。
