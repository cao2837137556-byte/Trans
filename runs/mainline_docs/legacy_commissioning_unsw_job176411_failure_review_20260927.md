## 已证明的代码缺陷，与未证明的实际触发点

审查 `legacy_unsw_archival_runtime_v1.Progress.guard/watch`、`launch_features` 和 `legacy_unsw_archival_common_v1.write` 发现：

1. JSON 状态通过 `status.json.next` 写入并原子替换。磁盘统计却先 `is_file()` 后独立 `stat()`；这两次调用之间文件正常改名消失，会产生 FileNotFoundError。这个异常进入与资源限额相同的停止路径。
2. 后台监控把异常仅保存在内存 `progress.error`，并 kill 所有子进程。若恰在主线程下一次 while 条件前完成停止，循环后的通用子进程检查直接抛 `FEATURE_WORKER_FAILED`，不再检查原始 `progress.error`。
3. 终态只落盘通用异常，缺少首个监控异常、traceback 和各 worker 退出码，且被停止的 worker 保留旧 RUNNING 状态。

本地两个确定性合成故障注入测试通过：验证临时文件消失可导致磁盘统计异常；验证监控停止四个模拟 worker 后，原始异常被上述通用异常覆盖，终态不再包含原始原因。测试不读取真实流量、不载入模型、不启动真实特征进程。

**这证明实现存在能产生此次表象的缺陷，不证明 Job 176411 的首个异常一定是临时文件竞争。** 返回日志已经丢失该异常，不能事后把推断写成事实。监控主动停止是与现有证据一致的强候选；文件系统异常、资源保护或外部信号仍需调度记录辅助排查。弃用警告本身不是此次失败证据。
