# Dense-reference immutable launch repair, prepared only

This independent overlay repairs two definite launch defects of failed job
179523. It neither changes scientific code nor grants permission to submit.
No remote operation, model forward, encoding, CAL, target evaluation, or new
Slurm submission is performed by preparing or testing these files.

## Evidence and exact scope

The fetched launch receipt reports `EXCEPTION_STOP`, stage `package_sha`, exit
1. Its actual GNU log ends `1492 listed files could not be read`, and filenames
are suffixed by CR. No synthetic-test log or science child was created.
The immutable outer manifest has 1492 CRLF records. GNU `sha256sum --check`
interprets those CR bytes as filename characters on this cluster.

Independently, frozen `src/chain.py` requires `FRESH_EXTERNAL_OUTPUT_REQUIRED`:
the science output must be fresh and outside the sealed package. The original
launcher used `package/runtime/job_ID/science`, so it would fail after passing
the outer hash check. This overlay uses the sibling path
`dense_reference_launch_repair_v1_20261027/runtime/job_ID/science` instead.

Evidence retained by the main chat:
`dense_reference_matrix_v1_20261027/deployment/LAUNCH_FAILURE_EVIDENCE_179523.json`.
The original failed attempt, archive, manifest, launcher, and approval remain
untouched. The original one-submission deployment helper must not be bypassed
or reset to reuse its spent submission lock.

## Files and trust gates

`verify_original.py` first hashes the untouched raw manifest against the pinned
hash, then removes at most one terminal CR from each LF-delimited record during
parsing only. It rejects internal CR, NUL, unsafe/noncanonical/duplicate paths,
missing or extra sealed files, symlinks, wrong counts, and content tampering.
It never writes a normalized manifest. It also checks the independent overlay
seal and both original/new approval identities before launch.

Runtime/private/local-progress paths and Python bytecode caches are excluded
from the sealed file-set comparison; they are not added to the approval scope.
The original directory is only read. All new receipts live in the sibling
overlay runtime. The already frozen downstream Python parsers use
`read_text().splitlines()` and accept CRLF; the only remaining shell hash check
uses an LF record generated by `printf` for the environment file.

`run_repair.slurm` retains the same amd partition, 1 node, 4 CPUs, 16 GiB,
CPU-only environment, thread limits, 12-hour wall limit, and no-requeue policy.
It runs the original synthetic tests and original `src/chain.py`, passing the
original private approval and exactly `runtime encode source_cal`. It cannot
run the target matrix. The original per-stage wall/RSS/disk guards remain in
the frozen chain. The package SHA gate still has a 180-second bound; synthetic
tests still have a 240-second bound.

The runtime parent directory must already exist. Each attempt uses exclusive
plain `mkdir`, so an existing job directory cannot be reused. `launch.json`
records each launch phase and any failure's exit code and source line. A zero
shell exit cannot count as success without `science/status.json=COMPLETE`.
The frozen `hpc/status_bridge.py` can read this sibling runtime with its `--root`
argument. No polling program or auto-submit loop is added here.

## Authorization boundary

`APPROVAL_TEMPLATE.json` is deliberately false and authorizes zero new
submissions. It is sealed with an explicit unresolved overlay-hash placeholder
to avoid a circular seal. After new explicit user authorization, a separate
private approval may bind the final `OVERLAY_SHA256SUMS` raw SHA, set the new
submission count to exactly one, and preserve all original identities and
stage/resource limits. It must remain outside the overlay's sealed member set.
No such authorized approval is created by this preparation.

Even a valid private approval is not an automatic retry mechanism. Submission
requires a separate one-shot controlled deployment step, recorded by the main
chat. No `sbatch` invocation is contained in this overlay. Scientific FAIL
continues its registered pairing; identity/data/numeric/resource exceptions
stop and preserve evidence. The third-pool full-matrix blocker remains.

## Local verification

Run `python -B -m unittest discover -s <overlay> -p test_launch_repair.py -v`.
Tests use synthetic data only, including a real GNU Bash reproduction of the
CRLF error and successful read-only verification of the same untouched bytes.
The host may skip the real filesystem-symlink case if Windows denies symlink
creation; a separate controlled symlink-flag test still checks rejection.
Validation receipts belong under `validation/`, outside the sealed members.

The original r2 package may additionally be hash-verified after fresh archive
extraction. This reads ordinary bytes only and performs no scientific work.
